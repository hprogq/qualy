你推荐单个批次的所有功能都放在一页上吗？即批次管理、阶段管理、参与名单、用户填报、公示查看、提交审核等页面，你推荐分成多个页面做，还是都放在单个页面的多个选项卡？

不推荐把“单个批次的所有功能”做成一个巨型页面，再靠一排 Tabs 切换。功能一多，这会迅速变成一个前端状态容器，路由、权限、数据加载、返回行为和角色语义都会混在一起。

更适合你的模型是：

> **Batch 是一个上下文容器；不同业务能力是独立页面。**
> 页面顶部可以共享同一个批次 Header 和二级导航，看起来仍然像“在同一个批次里操作”。

比如管理员进入某批次：

```text
2026-2027 学年综合素质测评                    进行中

[概览] [阶段] [参评人员] [审核] [公示] [设置]
────────────────────────────────────────────
                  当前页面
```

但是这些不是 React 本地 state 的 Tabs，而是真实路由：

```text
/assessment/batches/:batchId
/assessment/batches/:batchId/phases
/assessment/batches/:batchId/participants
/assessment/batches/:batchId/reviews
/assessment/batches/:batchId/publications
/assessment/batches/:batchId/settings
```

外观可以像 Tabs，架构上是 nested routes。

这样刷新：

```text
.../reviews
```

还是审核页面。

复制链接给另一个管理员，也直接进入审核页面。

浏览器后退也正常。

---

但我还会再拆一层：

**不是所有与 Batch 有关的业务都应该出现在这排管理员 Tab 里。**

尤其你提到的：

- 用户填报；
- 提交审核；
- 公示查看。

这些实际上有不同的“工作场景”。

我会按使用者的任务拆。

### 管理员的“批次管理空间”

主要是配置和运营：

```text
/assessment/batches/:batchId/overview
/assessment/batches/:batchId/phases
/assessment/batches/:batchId/participants
/assessment/batches/:batchId/publications
/assessment/batches/:batchId/settings
```

这里的心智模型是：

> 我正在管理这个批次。

---

### 学生的“我的填报”

不要做成：

```text
/batches/:batchId/submissions
```

然后和“阶段管理”并排成为管理员 Tab。

更自然的是独立工作区，例如：

```text
/assessment/my/batches/:batchId
```

或者：

```text
/assessment/batches/:batchId/my-submission
```

页面直接进入：

```text
2026-2027 综合素质测评

当前阶段：学生填报

我的材料
────────────────
...
```

学生根本不需要看到：

```text
阶段安排 | 参评人员 | 批次设置
```

因为那不是他的任务。

---

### 审核人员的“审核工作台”

同理，我更推荐：

```text
/assessment/batches/:batchId/reviews
```

或者如果审核工作量以后很复杂：

```text
/assessment/reviews?batch=:batchId
```

这取决于未来是否会出现“跨批次待办”。

如果审核员主要是：

> 进入一个批次，然后审核该批次所有材料

那就：

```text
/batches/:batchId/reviews
```

如果以后更像：

> 我的审核任务

那可以再有：

```text
/assessment/reviews
```

作为个人工作台。

两者不冲突。

---

### 公示也要区分“管理”和“查看”

管理员：

```text
/assessment/batches/:batchId/publications
```

这是：

> 公示管理

包含：

- 创建；
- 排期；
- 发布；
- 撤回；
- 修正版；
- 阶段联动。

普通用户访问的应该是：

```text
/assessment/batches/:batchId/publications/:publicationId
```

或者更偏用户工作区：

```text
/assessment/publications/:publicationId
```

这是：

> 查看一次已经发布的结果。

不要因为它们都叫 Publication，就强迫两个角色共享同一个 Tab 页面。

---

所以从 IA 上，我建议把整个系统看成三层。

第一层是模块：

```text
综合测评
```

第二层是资源/工作区：

```text
批次管理
我的填报
审核工作
公示
```

第三层才是单个 Batch 内部导航：

```text
概览
阶段
参评人员
审核
公示
设置
```

不一定每个角色都能看到所有入口。

---

你现在这个项目尤其不适合“所有东西一个页面”，还有一个架构原因：你正在往插件化拆。

例如未来：

```text
assessment-core
publication
review
appeal
```

如果整个 Batch 是一个大组件：

```tsx
<BatchPage>
  <PhaseTab />
  <ParticipantTab />
  <ReviewTab />
  <PublicationTab />
  <AppealTab />
</BatchPage>
```

那么 `assessment-core` 的 Batch 页面最终还是必须 import 所有插件 UI。

这等于插件边界又在前端被粘回去了。

更漂亮的是 Batch 提供一个 layout/route slot：

```text
BatchLayout
├── Overview
├── Phases
├── Participants
├── Review contribution
├── Publication contribution
└── Appeal contribution
```

各插件贡献自己的 route/navigation item。

例如 Publication 插件注册：

```ts
{
  path: 'publications',
  label: '公示',
  component: PublicationPage,
}
```

Batch Core 根本不需要知道 Publication 页面内部是什么。

这和你后端正在追求的低耦合方向是一致的。

---

我会控制 Batch 顶部导航的数量。大概 5～7 个以内问题不大，例如：

```text
概览
阶段
参评人员
审核
公示
设置
```

如果以后又出现：

```text
申诉
计分
日志
统计
附件
导出
```

就不要全塞到一排 Tab。

可以按业务分组：

```text
概览

运行
  阶段
  参评人员

业务
  审核
  公示
  申诉

管理
  设置
  操作记录
```

或者让低频项进入“更多”。

---

其中我觉得“概览”值得存在。

访问：

```text
/assessment/batches/:batchId
```

不一定非得 redirect 到 `/phases`。

现在功能少的时候阶段页当默认页还行，但随着审核、公示等功能加入以后，我会更推荐真正的：

```text
/overview
```

展示：

```text
2026-2027 综合素质测评             进行中

当前阶段
审核整理期
自 9 月 5 日 18:00 开始

下一阶段
第一次公示 · 待排期

参评人员
528 人

待审核
37 项

最近公示
尚未发布

近期操作
...
```

它承担“这个 Batch 现在怎么样”的作用，而 Phase 页面专心管理 Phase。

---

因此我最终会选：

**多个真实页面 + 一个共享的 Batch Layout + 页面顶部的二级导航。**

而不是：

**一个 URL + 一个巨大的 Tabs 组件。**

可以简单理解成：

```text
视觉上：像 Tabs
路由上：是页面
领域上：是插件能力
```

另外，“用户填报”和“公示查看”这类面向普通用户的任务，我不会强行放进管理员 Batch 管理导航里；它们应该拥有自己的用户工作流页面。这样管理员管理态、审核工作态和学生参与态不会混成一个超级页面。

我的意思是管理员的管理功能和用户的查询功能是否要分成两个完全不同的页面，还是都放到一个页面的不同选项卡和路由？还有审核功能，审核功能是应该放到管理员的功能里还是用户的功能里。还有公示和申诉等。

根据我的业务，你帮我看看是拆成几个页面更好？而且你拆开之后，一眼就能让用户看出来该点进去哪个链接，而不是思考这两个有什么区别

本站使用三级列表，一级为大分类，二级为带icon分类，三级为具体链接，如：系统管理——组织与用户——组织架构、用户管理、角色管理、用户类型

我建议明确拆成三个“工作空间”，而不是把所有功能都挂在“某个批次详情”的 Tabs 下面。

核心原因是你的系统实际上存在三种完全不同的任务视角：

- 配置和运营一个测评批次；
- 处理别人提交给自己的业务任务；
- 参与自己的综合测评。

这三者可能由同一个账号同时拥有，但不应该因此混成一个页面。

我会把三级导航直接设计成这样：

```text
综合测评
│
├─ 测评管理  [管理类 icon]
│  ├─ 批次管理
│  ├─ 阶段模板
│  └─ 时间线模板
│
├─ 业务处理  [待办/审核 icon]
│  ├─ 材料审核
│  └─ 申诉处理
│
└─ 我的测评  [用户 icon]
   ├─ 我的填报
   ├─ 结果公示
   └─ 我的申诉
```

我认为这比“管理员功能 / 用户功能”两个分类更好，因为**审核员既不是普通参评用户，也不一定是批次管理员**。

### 1. “测评管理”只放管理性质的东西

三级入口：

```text
测评管理
├─ 批次管理
├─ 阶段模板
└─ 时间线模板
```

点“批次管理”以后：

```text
/assessment/batches
```

看到所有有权管理的批次。

进入某个批次：

```text
/assessment/batches/:batchId
```

此时才出现这个 Batch 自己的局部导航：

```text
2026-2027 学年综合素质测评               进行中

[概览] [阶段安排] [参评人员] [公示管理] [设置]
──────────────────────────────────────────────
```

这些仍然是不同 URL：

```text
/assessment/batches/:batchId/overview
/assessment/batches/:batchId/phases
/assessment/batches/:batchId/participants
/assessment/batches/:batchId/publications
/assessment/batches/:batchId/settings
```

所以这里虽然视觉上像几个 Tabs，但实际上是 Batch 管理空间下的多个页面。

特别注意我会叫：

> **公示管理**

而不是“公示”。

这样和普通用户的：

> **结果公示**

一眼就能区分。

### 2. 审核绝对不要放进“测评管理”

这是我比较明确的建议。

因为“审核材料”不是“管理 Batch”。

现实中很可能：

```text
辅导员 A
有 review 权限
没有 batch.update 权限
```

如果导航设计成：

```text
测评管理
└─ 批次管理
   └─ 某批次
      └─ 审核
```

那么辅导员为了完成自己的审核任务，被迫进入一个叫“批次管理”的地方，非常别扭。

更麻烦的是，他会看到很多根本不属于他的管理概念：

```text
阶段安排
参评人员
归档
批次设置
```

因此审核应该成为独立工作区：

```text
业务处理
├─ 材料审核
└─ 申诉处理
```

点“材料审核”：

```text
待我审核                                       37

批次                     待审核       最近提交
2026 年综合素质测评        24          今天 17:21
2025-2026 第二学期测评     13          今天 15:06
```

再进去处理具体提交。

URL 可以是：

```text
/assessment/reviews
/assessment/reviews/:reviewId
```

或者：

```text
/assessment/reviews?batch=:batchId
```

这里 `batch` 作为筛选条件使用 query 就合理了，因为主要资源已经是 Review，而不是 Batch。

---

### 3. “申诉处理”我也放在业务处理，不放批次管理

因为它和材料审核本质很相似：

> 有人提交业务对象 → 某个工作人员处理。

所以：

```text
业务处理
├─ 材料审核
└─ 申诉处理
```

比：

```text
批次管理
├─ 审核
└─ 申诉
```

自然很多。

以后甚至可能出现：

```text
业务处理
├─ 材料审核         37
├─ 申诉处理          4
└─ 异常处理          2
```

它天然是一个工作台。

这还有一个很大的好处：可以做跨批次待办。

审核员真正想知道的往往不是：

> “2026 批次里面有没有我要审核的？”

而是：

> **“我现在还有什么要处理？”**

# 4. 普通用户全部进“我的测评”

这是第三个空间：

```text
我的测评
├─ 我的填报
├─ 结果公示
└─ 我的申诉
```

这三个名字我觉得已经足够没有歧义。

### 我的填报

进去看到：

```text
我的填报

2026-2027 学年综合素质测评
填报中 · 截止 9 月 5 日

[继续填报]
```

URL：

```text
/assessment/my/submissions
```

具体批次：

```text
/assessment/my/submissions/:batchId
```

或者：

```text
/assessment/my/batches/:batchId/submission
```

都可以。

---

### 结果公示

不是“公示”。

而叫：

> **结果公示**

进去就是阅读：

```text
结果公示

2026-2027 学年综合素质测评
第一次公示
发布时间：9 月 10 日 09:00

[查看结果]
```

用户不会把它和管理员的“公示管理”混淆。

### 我的申诉

这里只看自己的：

```text
我的申诉

第一次公示
成绩计算存在疑问
处理中

最终公示
—
```

包括：

- 新建申诉；
- 看处理进度；
- 看回复；
- 补充材料。

而工作人员处理这些东西进入：

```text
业务处理 → 申诉处理
```

于是：

```text
我的申诉
```

和：

```text
申诉处理
```

# 5. 公示因此会出现两个入口，这是正确的

你可能会担心：

```text
批次管理 → 公示管理
我的测评 → 结果公示
```

是不是重复？

不是。

它们虽然操作的是同一个 Publication domain，但任务完全不同：

```text
公示管理
= 创建、排期、发布、撤回、修正

结果公示
= 阅读已经对自己生效的公示
```

类似很多系统都会有：

```text
公告管理
```

和：

```text
通知公告
```

两个入口。

真正需要避免的是都叫：

```text
公示
```

让用户自己猜。

---

# 6. 审核也可以同时出现在 Batch 概览里，但只是“跳转”

这是一个细节。

虽然我不建议把“审核工作台”放在 Batch 管理内部，但 Batch 管理员查看概览时当然需要知道：

```text
待审核：37
```

所以 Batch Overview 可以有：

```text
审核进度

已完成    491
待审核     37
异常        3

[查看审核任务 →]
```

点击以后进入：

```text
/assessment/reviews?batch=xxx
```

也就是说：

> Batch 管理页可以展示业务状态和链接，但不需要拥有 Review 工作台本身。

同理：

```text
申诉中：4
[查看申诉处理 →]
```

进入：

```text
/assessment/appeals?batch=xxx
```

这样低耦合也更漂亮。

---

# 7. 公示管理为什么可以留在 Batch 管理内部？

这里和 Review 有一点不同。

因为 Publication 创建本身是典型的“运营这个批次”的动作：

```text
生成结果
创建公示
安排发布时间
决定是否联动下一阶段
撤回/修正
```

它天然需要 Batch 上下文。

所以我会允许：

```text
批次管理
→ 某批次
→ 公示管理
```

而不会把它强制拆成：

```text
业务处理 → 公示发布
```

不过如果未来出现专门负责全校发布的角色，也可以额外贡献一个全局“公示管理”入口。这不是第一版需要解决的。

# 8. 你的三级菜单我最终建议就三个二级分类

不要拆成五六个二级分类，否则侧栏本身又复杂了。

最终：

```text
一级：综合测评

二级：测评管理
  三级：批次管理
  三级：阶段模板
  三级：时间线模板

二级：业务处理
  三级：材料审核
  三级：申诉处理

二级：我的测评
  三级：我的填报
  三级：结果公示
  三级：我的申诉
```

这是我最推荐的一版。

权限控制以后，一个普通学生可能只看到：

```text
综合测评
└─ 我的测评
   ├─ 我的填报
   ├─ 结果公示
   └─ 我的申诉
```

审核员：

```text
综合测评
├─ 业务处理
│  ├─ 材料审核
│  └─ 申诉处理       // 有权限才显示
│
└─ 我的测评          // 如果他自己也是参评者
```

学院管理员：

```text
综合测评
├─ 测评管理
│  ├─ 批次管理
│  ├─ 阶段模板
│  └─ 时间线模板
│
├─ 业务处理
│  ├─ 材料审核
│  └─ 申诉处理
│
└─ 我的测评          // 如果本人也是参评对象
```

一个账号同时看到三块也完全不冲突，因为三个名字表达的是三个动作视角。

---

还有一个我认为值得坚持的命名原则：

```text
批次管理       → 我在配置/运营
材料审核       → 我在处理任务
申诉处理       → 我在处理任务
我的填报       → 我自己的数据
我的申诉       → 我自己的数据
结果公示       → 我在阅读
公示管理       → 我在发布/维护
```

尽量不要使用这种模糊名称：

```text
批次
审核
申诉
公示
测评中心
综合管理
业务中心
```

因为单独一个名词没有告诉用户“进去之后我要干什么”。

所以如果按你的业务和现有三级列表结构，我会选 **三个工作空间、六到八个明确三级入口；单个 Batch 再有自己的局部子路由**。这比“管理员一套页面 + 用户一套页面”更准确，也比“一个 Batch 超级页面塞所有 Tabs”更容易理解。

申诉和审核我寻思放在一起了，因为都是审核，无非是底下的按钮不一样，更方便些。然后还有就是班级负责人、专业负责人、年级负责人有的是可以查看班级/专业/年级内同学的填报情况的，比如填报完成率、审批中和已通过的数量、帮助代填等，这个也需要单独做个页面。

最后再帮我规划下左侧的navbar分层和URL的设计就行，不需要讲太多为什么这么设计。二级页面下也可以没有三级页面。

我会最终收敛成 4 个二级入口，职责比较清楚，而且用户基本不用思考“这个功能到底在哪”。


学生时间线页你推荐怎么设计？

学生侧我不建议复用管理员那种“类表格阶段安排”。管理员关心“怎么配置”，学生关心的是三个问题：

> **现在进行到哪了？我现在要做什么？后面大概还有什么？**

所以学生侧更适合真正的“进度时间线”，而且我建议把它作为单个测评详情页的主体，而不是再搞一堆配置味很重的字段。

我会设计成这样：

```text
2026-2027 学年综合素质测评                         进行中

当前：学生填报期
请在 9 月 5 日 18:00 前完成材料填报并提交。

[继续填报]

────────────────────────────────────────

测评进度

✓  学生填报期
   9 月 1 日 08:00 开始
   当前进行中

   填写并提交本学年的综合素质测评材料。
   截止：9 月 5 日 18:00

   ┃

○  审核整理期
   预计 9 月 5 日 18:00 开始

   学院将审核已提交的材料。
   审核期间如需补充材料，会通知你。

   ┃

○  第一次公示
   时间待定

   审核完成后将发布第一次测评结果。

   ┃

○  申诉期
   时间待定

   第一次公示后，如对结果有异议，可在规定时间内提出申诉。

   ┃

○  最终结果
   时间待定
```

这里有几个我认为很重要的原则。

第一，学生侧不要出现“排期”“未排期”“外部来源”“由公示设置”“锁定”这种管理术语。

管理员看到：

```text
PhaseSchedule
plannedEntryAt = null
entryNote = "待审核完成后开始"
```

学生只看到：

```text
时间待定
审核完成后开始
```

或者：

```text
预计 9 月 10 日开始
```

实现细节全部隐藏。

第二，学生侧可以显示“阶段结束时间”，但它只是展示值。

例如后台：

```text
填报期开始：9/1
审核期开始：9/5
```

学生看到：

```text
学生填报期
9 月 1 日 08:00 — 9 月 5 日 18:00
```

完全没必要告诉学生：

> “9 月 5 日其实是下一个 Phase 的 `plannedEntryAt`。”

对学生来说它就是截止时间。

所以可以做一个 student projection：

```ts
start = phase.actual/planned entry
end = nextPhase.actual/planned entry
```

然后直接展示自然语言。

第三，我会特别突出“当前阶段”，弱化历史和未来阶段。

视觉层级：

```text
过去
✓ 灰色，小

当前
● 高强调
  说明
  时间
  当前可执行动作

未来已排期
○ 普通

未来未排期
○ 弱化
  时间待定
  说明
```

例如：

```text
✓ 材料填报
  9/1 — 9/5

● 材料审核                         当前
  9/5 开始
  学院正在审核你的材料。

  当前状态：审核中
  [查看我的材料]

○ 第一次公示
  时间待定
  审核完成后发布
```

学生一眼就能找到现在的位置。

第四，阶段的 `description` 很适合直接用在这里，但我建议把它明确成“面向参与者的阶段说明”。

比如：

```text
阶段名称
材料审核

阶段说明
学院将审核你提交的材料。如需补充或修改，会通过系统通知你。
```

这就很有价值。

如果管理员还需要写：

```text
本阶段由年级负责人负责推进，发现 BLOCKED 后联系 XX
```

那应该另开：

```ts
internalNote
```

不要和学生可见的 `description` 混用。

第五，当前阶段应该带“我的状态”，而不只是 Batch 状态。

这是学生时间线最有价值的地方。

例如 Batch 当前都是“审核期”，但对于不同学生：

```text
张三：
材料审核
✓ 已通过

李四：
材料审核
审核中

王五：
材料审核
需要补充材料
[补充材料]
```

所以当前节点可以有两层：

```text
● 材料审核                  当前阶段

  本阶段状态
  需要补充材料

  审核意见：
  请补充竞赛获奖证书原件照片。

  [去补充]
```

这样“时间线”不只是装饰，而成为学生真正的任务入口。

第六，公示和申诉不要在时间线上塞完整业务页面，只做状态和跳转。

例如：

```text
✓ 第一次公示
  9 月 10 日 09:00 发布

  你的第一次测评结果已经发布。
  [查看结果]
```

下一阶段：

```text
● 申诉期
  9 月 10 日 — 9 月 13 日

  如对第一次公示结果有异议，可以提交申诉。
  [发起申诉]
```

如果已经申诉：

```text
● 申诉期

  我的申诉：处理中
  [查看申诉]
```

这样和你前面规划的：

```text
我的填报
结果公示
我的申诉
```

并不冲突。

时间线负责：

> 告诉我现在发生什么，并给入口。

具体业务页负责：

> 完成这件事。

第七，未来没有排期的阶段我仍建议显示，但不要显示得像异常。

不要：

```text
第一次公示
⚠ 未排期
```

而是：

```text
第一次公示
时间待定
审核完成后发布
```

这是正常业务状态，不应该出现 warning。

如果 `entry_note` 有内容：

```text
plannedEntryAt = null
entryNote = "待学院审核全部完成后开始"
```

学生侧可以直接：

```text
时间待定
待学院审核全部完成后开始
```

如果没 note：

```text
时间待定
具体时间将另行通知
```

第八，如果某些阶段纯属后台内部处理，我不一定建议全部原样暴露。

例如内部可能有：

```text
成绩重算准备
快照冻结
公示准备
异常清理
```

学生没必要知道这么细。

这里可以给 Phase 一个：

```ts
participantVisible: boolean
```

或者更一般地通过已有 scope / profile 决定展示。

学生最终可能看到：

```text
填报
↓
审核
↓
第一次公示
↓
申诉
↓
最终结果
```

而管理员内部可能实际有：

```text
填报
审核
审核整理
第一次公示准备
第一次公示
申诉
申诉处理
最终结果生成
最终公示
```

我不会为了“数据库时间线必须完全一致”而牺牲学生端的信息架构。

不过第一版如果你的阶段数量本来就不多，也完全可以先全部展示，不急着引入 `participantVisible`。

最后，我会让单个学生批次页面大概长这样：

```text
2026-2027 学年综合素质测评

当前阶段：材料审核
我的状态：需要补充材料

请在审核人员要求的时间内补充相关证明。

[补充材料]

──────────────────────────────────

我的测评进度

✓  材料填报
   9 月 1 日 — 9 月 5 日
   已于 9 月 4 日 18:32 提交

●  材料审核                         当前
   9 月 5 日开始
   需要补充材料
   [查看审核意见]

○  第一次公示
   时间待定
   审核完成后发布

○  申诉期
   时间待定
   第一次公示后开放

○  最终结果
   时间待定
```

页面最上面负责“现在该干嘛”，下面时间线负责“整个流程走到哪”。

我认为学生侧这样就够了，甚至不需要再单独设计一个复杂的“阶段详情”页面。

你推荐学生侧的时间线横向还是纵向展示？我觉得不要展示什么“需要补充材料”吧，这个东西应该放到工作台/收件箱/待办任务里，不应该展示在时间线上，时间线就是让用户直观看到批次当前的进度，如有需要可以加当前进度结束倒计时什么的。这也只是页面的一部分。

时间线应该展示在用户的哪个/哪些页面上？还是展示在用户侧批次每个页面的顶部banner上？

对，我同意你的修正：**时间线只表达 Batch 的宏观业务进度，不承载“我的任务状态”**。补材料、审核意见、申诉待处理之类应该进入待办/收件箱/工作台，否则时间线会从“进度指示器”退化成另一个任务中心。

我更推荐：**桌面端横向，移动端纵向或横向可滚动；不要桌面端做纵向。**

你的阶段天然是严格有序的，而且学生看它的主要目的只是回答：

> 现在到哪一步了？前面经历了什么？接下来还有什么？当前阶段大概什么时候结束？

横向更像一个真正的 process stepper：

```text
✓ 填报          ● 审核            ○ 第一次公示        ○ 申诉          ○ 最终结果
9/1—9/5         进行中             时间待定            时间待定         时间待定
───────────────●──────────────────○──────────────────○───────────────○
                剩余 2天 6小时
```

而不是纵向：

```text
✓ 填报
│
● 审核
│
○ 公示
│
○ 申诉
│
○ 最终结果
```

纵向更适合“事件历史”“物流轨迹”，但你这里的时间线只是页面的一部分，纵向会吃掉很多垂直空间。

如果阶段通常是 4～7 个，横向尤其合适。

```text
资源库
/resources
```

里面放：

```text
测评资源
├─ 政策管理
├─ 题型管理
├─ 阶段模板
└─ 时间线模板
```

URL：

```text
/resources/policies
/resources/item-types
/resources/phase-templates
/resources/timeline-templates
```

或者如果你的“题型”不是 item type 而是真正的一类指标/表单定义，再按领域名调整 URL。

“资源库”这个名字有几个好处：

```text
政策
题型
模板
```

明显都是：

> 创建一次 → 多个 Batch 复用。

而且它完全不暗示：

> 只有管理员能改。

老师、辅导员、年级负责人根据 RBAC 可以：

```text
只读
创建
编辑自己范围
管理某组织范围
```

都很自然。

例如普通学生根本看不到“资源库”。

辅导员可能看到：

```text
资源库
├─ 政策管理
├─ 阶段模板
└─ 时间线模板
```

某老师有题型创建权限，则再出现：

```text
题型管理
```

这与你现在 capability-based 权限模型非常一致。

---

### 四、组织与权限

这个我建议真的从原来的“配置中心”里独立出来。

```text
组织与权限
/organization
```

因为它跟政策/题型/模板不是一个性质。

里面：

```text
组织与权限
├─ 组织架构
├─ 用户管理
├─ 角色管理
└─ 用户类型
```

URL：

```text
/organization/tree
/organization/users
/organization/roles
/organization/user-types
```

名称我倾向 **“组织与权限”**，而不是“组织与用户”。

因为：

```text
组织架构
用户
角色
用户类型
权限
```

已经不只是用户管理。

如果未来“角色管理”非常系统级，而年级负责人只管理自己辖区用户，也没有问题。Navbar 根据 capability 输出：

辅导员可能只看到：

```text
组织与权限
├─ 组织架构
└─ 用户管理
```

系统级管理员则看到完整：

```text
组织架构
用户管理
角色管理
用户类型
```

所以仍然不需要 `/admin`。

## 那真正的“配置管理”去哪？

这里我建议你不要为了已有一个叫“配置管理”的功能，就硬保留一个一级“配置中心”。

应该先看它到底配置什么。

如果是：

```text
综测默认参数
默认计分规则
业务开关
```

它可以属于：

```text
资源库
└─ 测评设置
```

如果是：

```text
站点名称
邮件
认证
存储
插件
```

才属于真正的：

```text
系统设置
```

而且“系统设置”可以只对极少数人出现，甚至放头像菜单或更多菜单：

```text
用户 ▼
├─ 个人设置
├─ 系统设置     // 有权限才出现
└─ 退出
```

没必要为了低频系统管理员功能占一个永久顶部 Tab。

## 顶栏和 Batch Context Bar 最终可以长这样

全局：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Qualy     测评     工作台     资源库     组织与权限            🔔   张三 │
└─────────────────────────────────────────────────────────────────────────┘
```

进入 Batch：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Qualy     测评     工作台     资源库     组织与权限            🔔   张三 │
├─────────────────────────────────────────────────────────────────────────┤
│ ← 全部测评   [ 2026—2027 学年本科生综合素质测评 ▾ ]                    │
│              进行中 · 当前：审核整理期 · 剩余约 4 天                    │
└─────────────────────────────────────────────────────────────────────────┘
```

下面才是：

```text
BatchSidebar | PageContent
```

这时候顶部 4 个入口数量刚好，不会像之前只有“测评 / 配置中心”两个那么空，同时每个入口也确实代表一个相对独立的工作空间。

我尤其推荐 **“资源库” + “组织与权限”分开**。前者是综测业务资产，允许权限下放；后者是平台身份、组织和授权基础设施。这两个东西在领域上就不应该继续放在同一个“配置中心”里。
