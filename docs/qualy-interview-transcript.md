# 第一幕：先让面试官理解它值不值得做

## 1. 项目介绍

**面试官**：先介绍一下你做的项目。

**我**：好的。这个项目叫 Qualy，是一套面向高校综合素质测评的系统。它处理的核心问题，可以概括成一句话：一项会影响奖学金、评优和推免的成绩，怎样从学生提交的材料，经过多人审核和规则计算，最终形成一份任何人都能追溯的结果。

学校现在常见的做法是收 Excel、收压缩包，再由不同层级的工作人员人工合并。这个流程一旦持续几周，就会出现几个很现实的问题。材料改过几次说不清，审核人更换后待办容易丢，学院规则变化后历史成绩可能被新规则影响，学生对零点零一分有异议时，也很难解释这一分来自哪条材料、哪次认定和哪个版本的规则。

我把 Qualy 做成了一个全栈 TypeScript 单体应用。学生负责填报和查看结果，班级、年级、学院的工作人员负责审核、复查和批次管理。系统保留每次填报版本、每次审核决定、最终认定和计分明细。技术上，后端统一使用 Effect 管理依赖、失败和资源生命周期，数据库使用 PostgreSQL，浏览器端使用 React 和 Vite。

这个项目最值得展开的地方有三个。第一，接近三十个启用插件通过统一描述进行组装，登录、数据库、权限、界面和综测业务都能声明自己的能力与依赖。第二，从数据库查询、服务、接口契约到前端调用，成功结果和业务失败都沿同一份类型传递。第三，发布时会锁定本次产品的插件集合和浏览器可见功能，新旧页面与服务端无法安全配合时会明确阻止继续操作。

如果您希望看代码，我会先打开一个六十多行的示例插件。它能在一屏内展示一张表、一个接口和一个页面怎样进入整个产品。

## 2. 三十秒版本

**面试官**：如果只用三十秒呢？

**我**：Qualy 把高校综测里分散的材料、审核、认定、计分和公示整理成一条可追溯流程。我用全栈 TypeScript、Effect 和 PostgreSQL 实现了插件化组装、严格的错误与依赖类型、按组织范围授权、精确计分和可审查发布。它的重点是让复杂规则能够被系统执行，让每一个结果都能解释来源。

## 3. 为什么这个业务有技术深度

**面试官**：听起来还是填表、审批、算分，复杂度主要在哪里？

**我**：复杂度集中在规则随时间变化、多人并发处理和结果必须可解释这三件事上。

第一，学校给出统一框架，各学院会制定细则。同一类加分项可能拥有不同字段、不同材料要求和不同审核路线。我把稳定机制写成代码，比如题型、审核链和计分组合；具体学院细则保存为版本化配置。这样新增一条细则通常是配置动作，代码仍然保留统一约束。

第二，权限跟组织位置有关。一个辅导员可以管理某个年级下的学生，班委只能处理本班范围。列表查询需要把这个范围直接下推到 SQL，分页、计数和授权才能同时正确。结构写入还要面对并发，例如管理员等待数据库锁时，他的权限可能刚好被另一请求撤销，所以系统会在锁内再次确认。

第三，历史必须稳定。学生每次修改产生新的填报版本，审核流程保留事件，终局认定独立保存，计分规则也带着固定身份。管理员后来修改规则，历史结果仍按当时冻结的事实解释。

第四，分数需要精确。系统内部把分数放大一万倍存成整数，组合时处理求和、取最高、取前几项、封顶和保底，展示前再统一舍入。整个过程中不会让 JavaScript 浮点数进入权威计分路径。

**面试官**：为什么强调认定和计分分开？

**我**：审核人员回答的是事实成立到什么程度，例如奖项级别、名次和材料日期。计分规则再把这些已认定事实换算成分数。两层分开后，规则调整不会篡改审核历史，审核人员也无需直接填写一个缺少来源的分值。出现争议时，我可以先回答系统认定了什么，再回答当时的规则怎样计算。

**备注**

- 这里可以根据面试官反应选择一个方向继续。
- 对方关注业务时，转到版本、审核和精确计分。
- 对方关注工程时，转到插件和 Effect。
- 对方关注安全时，转到租户、SQL 授权和锁内复核。

## 4. 插件在代码里是什么

**面试官**：你一直说插件，给我看一下具体代码。

**我**：我打开仓库里最小的 ping 插件。它是演示用功能，代码很短，正好能看清一个插件怎样声明自己的数据库表、页面和接口。

**现场展示**

- packages/plugins/demo/ping/src/index.ts 第 18 到 65 行。
- 先指第 49 行 Plugin.define，再依次指第 51 到 62 行。

**我**：Plugin.define 生成一份插件描述。第一个参数是插件身份，第二部分声明它依赖数据库和界面登记能力。后面的每一项是它交给产品的一份贡献。

Db.entities 声明一张 PingLog 表。Ui.page 声明一个页面，包括稳定页面编号、地址、组件、所用布局和可见范围。Api.group 把接口契约与处理函数登记给 HTTP 能力。

这个入口文件加载时只创建普通描述值，不会连接数据库，也不会启动服务器。真正占用资源的动作由应用宿主在收齐全部插件后统一执行。这个特点让我可以在启动前检查依赖缺失、重复提供和环形依赖。

**我**：这份文件只定义接口形状。它声明 GET /ping/hello，查询参数 name 可选，成功结果含 msg 字段。前端会直接使用这份定义获得调用类型，服务端也根据同一份定义挂处理函数和生成接口文档。

**现场展示**

- packages/plugins/demo/ping/src/index.ts 第 27 到 47 行。

**我**：这里是处理函数。第 31 行读取问候语配置，读取发生在这一组处理函数构建时，配置错误会阻止应用完成启动。第 33 行取得数据库能力。第 36 行给函数一个稳定名字，运行时可以把它放进链路追踪。第 41 行用带类型的查询构建器写入记录。

**我**：页面通过插件自己的 typed client 获得 query.ping.hello。参数和返回值从刚才的接口定义推导，页面没有手写一份重复类型，也没有生成一套额外客户端代码。

所以我对插件的定义很具体：它是一个普通包，通过纯描述告诉系统自己依赖什么、提供什么。系统负责校验、排序、构建和释放。

## 5. 和普通模块化有什么差别

**面试官**：这和普通的代码模块有什么差别？

**我**：普通模块主要解决源码怎样分文件。这里还要解决产品由哪些能力组成、这些能力何时构建、谁负责解释贡献、失败后怎样释放资源。

举一个页面的例子。业务插件只提交页面描述，界面登记插件负责检查页面编号、路径和布局约定，再生成按当前用户过滤的页面清单。宿主只负责把贡献交给负责人，不需要理解页面业务。数据库实体、权限目录、登录方式和命令行能力也用同一套模式。

因此模块边界同时参加了启动校验和发布校验。某个插件缺少依赖，或者两个插件争用同一个单一提供能力，系统会在提供服务前失败，并且错误会点名冲突双方。

## 6. 为什么选择单体加插件

**面试官**：有这么多插件，为什么不拆成微服务？

**我**：这个业务的写入经常需要同一事务。例如一次审核可能同时追加审核事件、写最终认定、更新条目状态并记录领域历史。拆成多个进程后会引入分布式事务、消息补偿和跨服务权限一致性，对当前规模的收益有限。

我保留单体部署和单库事务，再用插件提供编译期依赖约束、运行时装配和浏览器分包。模块隔离和部署拓扑分开考虑，能控制复杂度，也方便独立测试。

我还给插件化设了清晰上限。插件集合在一次发布中固定，运行期间不会热安装。学院细则使用配置表达，避免把每条业务政策做成代码插件。

# 第三幕：插件怎样进入一个发布

## 7. 系统怎样找到所有插件

**面试官**：系统怎样知道要加载哪些插件？

**我**：仓库根目录有一份产品配置文件 qualy.yml。它列出当前产品选择的插件，以及会改变产品结构的非敏感配置。包管理文件决定哪些插件已经安装，qualy.yml 决定这次产品选择哪些。

解析时，系统按包名找到每个插件的描述，核对包名与插件身份，校验配置，检查依赖，再收集数据库实体、权限代码等需要固化的结构贡献。当前 qualy.yml 里有三十个插件条目，其中一个验证码提供方处于关闭状态。

密码、数据库连接串和云端密钥不写在这份文件里。它们从部署环境读取，也不会进入解析结果。

**现场展示**

- qualy.yml 第 1 到 20 行，说明产品配置与运行配置的区别。
- qualy.yml 第 27 到 42 行，展示存储能力与具体后端分离。
- qualy.yml 第 74 到 94 行，展示邮件后端和验证码提供方选择。

## 8. 为什么需要 qualy.lock.json

**面试官**：有配置文件以后，为什么还需要锁文件？

**我**：配置文件表达人的选择，锁文件保存机器解析后的结果和指纹。它和依赖锁文件的思路相似，关注点是产品组成。

例如某个插件新增一张表或一个权限代码，配置文件可能一字未改，解析结果已经发生变化。qualy.lock.json 会在代码评审里展示这类差异。当前锁文件能看到每个活跃插件的状态、版本和重要结构贡献，例如综测插件贡献的实体与权限代码。

生产启动时会重新解析，再和已评审锁文件比较。发现漂移就拒绝启动。开发环境会给出警告，方便本地编辑配置。启动过程只负责校验和运行，修复锁文件需要开发者显式执行解析命令并审阅差异。

**现场展示**

- qualy.lock.json 顶部的 manifestHash、resolutionHash 和 plugins。
- apps/server/src/verify-assembly.ts 第 10 到 40 行。

**我**：这里的注释写得很直接。启动如果自动重算并覆盖锁文件，评审过的内容会失去约束力。所以生产环境发现不一致就停止。

## 9. 如何避免核心代码认识所有插件

**面试官**：最后总要有个地方把数据库插件、权限插件和业务插件列出来吧？

**我**：产品选择集中在 qualy.yml，服务端宿主代码本身没有业务插件名单。它读取已经验证的解析结果，动态导入各个描述，再交给统一组装器。

宿主只认识少量通用概念：服务、扩展登记表、贡献和组装阶段。它不认识数据库表、页面或权限代码的业务含义。每种能力由自己的提供插件解释。例如数据库插件负责把实体贡献变成 ORM 元数据，界面登记插件负责把页面贡献变成用户可见清单。

**现场展示**

- apps/server/src/runtime.ts 第 31 到 42 行。
- packages/core/plugin-kit/src/index.ts 第 3 到 16 行。

## 10. 扩展点怎么解释

**面试官**：你说的扩展登记表具体是什么？

**我**：可以把它理解为一张有负责人、有字段类型、有处理时机的登记表。

页面登记表允许很多插件登记页面，界面能力是唯一负责人。负责人拿到所有页面以后做校验和投影。数据库实体登记表允许很多插件登记实体，数据库能力负责构建 ORM 元数据。

一张表可以有很多贡献方，只允许一个负责人。两个负责人会让解释规则不确定，组装器会点名双方并拒绝。存在贡献却找不到负责人时也会拒绝，避免贡献静默丢失。

**现场展示**

- packages/core/plugin-kit/src/index.ts 第 62 到 154 行。
- packages/core/plugin-kit/src/assemble.ts 第 78 到 154 行。

## 11. 组装为什么分阶段

**面试官**：拿到全部描述后怎样变成一个可运行服务？

**我**：组装分四类时机，我现场会把它们归纳成三个主要层次和一个外部层次。

第一层处理纯静态贡献，例如实体、接口契约和目录。它不依赖运行中的服务，生成迁移或接口文档时也能复用。

第二层构建服务，例如数据库连接、权限判断和存储能力。带明确身份的服务按依赖拓扑排序，有环会失败。

第三层建立需要运行中服务的绑定，再挂最终处理函数。例如一个登录方式需要调用数据库服务，它会在服务完成后注册。

外部层次交给另一个宿主解释，例如命令行能力。服务端启动不会因此加载迁移器或部署工具。

所有层次完成后才越过启动屏障。端口在短暂准备窗口会明确返回 503，路由完整后再服务真实请求。启动中途失败时，已经获得的资源会沿 Effect 的作用域释放。

**现场展示**

- packages/core/plugin-kit/src/index.ts 第 35 到 60 行。
- packages/core/plugin-kit/src/assemble.ts 第 12 到 43 行。
- apps/server/src/runtime.ts 第 31 到 42 行和第 167 到 175 行。

# 第四幕：前端插件怎样进入浏览器

## 12. 页面组件怎样被收集

**面试官**：后端可以动态装配，React 页面怎样进入前端？

**我**：浏览器构建读取同一份产品解析结果，找到所有活跃插件声明的页面、布局、插槽组件和登录方式，然后生成一份私有组件表。

这里用了 Vite 虚拟模块。业务代码导入 virtual:qualy/plugins，磁盘上没有这份源码。Vite 插件在构建时生成内容。生成结果包含四类加载表：页面、布局、插槽和登录方式。每个值都是动态 import，所以页面能够按需拆包。关闭的插件不会出现在表里，对应组件也不会进入浏览器产物。

**现场展示**

- packages/build/web/src/collect.ts 第 137 到 173 行。
- packages/build/web/src/vite.ts 第 23 到 74 行。

**我**：收集器还会生成一份只供依赖扫描使用的静态 import 副本。它解决了 Vite 冷启动扫描看不到动态组件树的问题。真正运行时仍使用动态加载，扫描副本只帮助 Vite 在应用执行前发现完整依赖。

## 13. 为什么组件表保持私有

**面试官**：服务端会把组件路径发给浏览器吗？

**我**：浏览器只接收稳定页面编号、布局编号和插槽编号。组件来自哪个包、哪个源文件，由构建产物内部的私有表决定。服务器不会下发源码路径或包名。

这样做有两个好处。第一，公开协议不会绑定仓库目录结构。第二，按用户返回的页面清单只描述用户能看到的产品入口，组件实现仍由当前 release 决定。

## 14. manifest 用通俗语言怎么解释

**面试官**：你提到页面清单，它和刚才的组件表有什么差别？

**我**：组件表回答这个前端包里有哪些实现。页面清单回答当前用户现在能看到哪些入口。

用户打开应用后，服务端根据登录状态、权限范围和产品配置返回页面、导航、布局、插槽内容和登录方式。前端用稳定编号在私有组件表里找到对应实现，再生成路由。

页面清单负责减少无效入口和敏感功能暴露。接口处理仍然会重新验证身份、租户、资源和权限。即使用户手工构造请求，也无法依靠隐藏菜单绕过服务端授权。

**现场展示**

- packages/web/runtime/src/route-builder.tsx 第 95 到 170 行。

## 15. shell、layout 和 slot 是什么

# 第五幕：Effect 深挖

## 16. Effect 是什么

**面试官**：你多次提到 Effect，我没有用过。它解决了什么问题？

**我**：我会把 Effect 解释成一种可以组合的程序描述。普通 async 函数的 Promise 类型主要告诉我成功值，函数可能抛出什么、依赖什么服务、资源怎样释放，通常分散在实现和约定里。

Effect 的核心类型可以读成 Effect<成功结果, 可预期失败, 运行依赖>。例如读取组织节点可以返回节点视图，失败类型包含节点不存在和无权访问，运行时需要组织服务。调用方组合多个 Effect 时，编译器会继续计算结果、失败和依赖。

它依然可以写成接近顺序代码的形式。Effect.gen 提供生成器写法，yield* 表示等待前一步并继续传播它的失败与依赖。团队理解业务流程时，阅读体验和 async/await 很接近。

## 17. 为什么整个后端统一使用 Effect

**面试官**：Express 加依赖注入库和错误处理中间件也能做，为什么选 Effect？

**我**：我关注的是几个横切问题能否共享一套执行模型。

Qualy 有接近三十个启用插件，每个插件可能提供服务、打开连接、启动后台任务、声明失败并参与链路追踪。如果分别用依赖注入、异常约定、关闭钩子和监控包装，很容易出现四套规则互相错位。

Effect 把依赖、可预期失败、取消、资源生命周期、日志和追踪都放到同一运行模型中。一个业务函数返回 Effect 后，外层可以决定提供哪些服务、怎样重试、怎样超时、怎样记录、何时执行。业务服务本身不会私自启动运行时。

这个选择也有代价。新成员需要理解生成器、三条类型通道和 Layer。Effect v4 目前仍是预发布版本，升级可能带来接口变化。我的应对包括锁定精确版本、保存同版本上游源码身份、用小型运行时探测核对不稳定行为，并把 Effect 语言服务接入正式类型检查。

## 18. Context 如何做类型安全依赖注入

**面试官**：依赖怎样注入？

**我**：Context 可以理解成按唯一类型身份保存服务的环境。每项服务定义一个身份牌和接口类型。业务代码 yield* 这个身份牌，就能拿到服务；同时函数的依赖类型会出现这项服务。

例如 Orm 是数据库服务身份。组织服务的 make 函数在构建阶段取得数据库提供器、权限服务、人员站位服务和审计服务。最终服务方法对调用者只暴露成功与业务失败，底层依赖已经由 Layer 闭合。

## 19. Layer 是什么

**面试官**：Layer 又是什么？

数据库 Layer 会读取配置、创建连接池、提供 Orm 服务，并注册作用域关闭时的释放动作。测试可以替换为临时数据库 Layer，业务函数无需修改。多个 Layer 组合时，框架会复用已经构建的服务，应用关闭时统一收束作用域。

## 24. Fiber、Scope 和优雅关闭

**面试官**：Effect 对并发和关闭有什么帮助？

**我**：Fiber 可以理解为可取消的轻量执行单元。请求和后台任务运行在 Fiber 上，日志标记与追踪上下文会随执行关系传播。Scope 表示资源存活范围，Layer 打开的资源会把清理动作放进 Scope。

服务进程收到关闭请求后，会先停止继续接收工作，给正在处理的请求一个有限排空时间，然后关闭连接、后台任务和监控导出。某个资源释放过慢时，插件组装层会在日志里标出进入释放和完成释放的插件，方便定位卡住的位置。

HTTP 层还有一个实践细节。空闲长连接和事件流可能让 Node 的 server.close 等很久，所以停止阶段会持续清理空闲连接，并在短暂宽限后切断剩余连接。客户端对事件流断开有重连逻辑。

## 25. Effect 在哪里真正执行

**面试官**：这些描述最终在哪里运行？

## 26. Effect 选型的克制回答

**面试官**：如果重新做一次，你还会选 Effect 吗？

**我**：如果项目仍然需要大量插件组合、严格失败类型、资源生命周期和统一追踪，我会继续考虑 Effect，因为这些收益在 Qualy 已经形成真实代码和门禁。

我不会把它当成所有 TypeScript 项目的默认答案。一个短生命周期的小型接口服务，用普通 async 函数可能更容易招聘和维护。Qualy 的收益来自复杂关系长期存在，技术投入才有回报。

升级风险也需要持续管理。当前版本是 v4 预发布，项目把上游源码版本、提交和内容哈希锁定下来。遇到不稳定 API 时以 vendored 源码和测试核对，升级独立提交并重跑全套门禁。

- Effect 是全场最适合深入的方向，回答时始终回到 Qualy 里的真实问题。

# 第六幕：从数据库到浏览器的类型链路

## 27. 全链路类型怎样成立

**面试官**：你开场说从数据库到前端都有类型，具体经过哪些层？

**我**：我会按六层说明。

第一层是表结构。MikroORM 实体定义字段、索引、外键和约束，迁移工具比较已提交历史与当前目标结构。

第二层是查询。插件通过 Db.scope 获得只包含自己实体的 Kysely 类型。表名或字段名写错会在类型检查时失败。组织插件需要其他插件的数据时，通过服务接口协作，不直接跨插件查询表。

第三层是领域服务。函数返回 Effect，成功值和业务失败形成显式类型。

第四层是 HTTP 契约。Effect Schema 同时提供 TypeScript 类型和运行时编解码。路径、请求体、响应和业务错误集中声明。

第五层是插件私有前端客户端。浏览器引用契约文件，通过 Api.local 和统一 runtime 得到方法，参数、返回值与失败类型自动推导。

第六层是 React 组件。查询和 mutation 钩子保留这些类型，页面只处理领域失败，平台失败由统一 runtime 呈现。

## 28. 为什么仍然需要运行时校验

**面试官**：TypeScript 已经有类型，Schema 有什么用？

**我**：TypeScript 类型在编译后不会留在网络边界。浏览器请求、第三方客户端、旧版本页面和数据库内容都属于运行时数据，需要实际解码。

Schema 会在请求进入时校验路径、查询和请求体，在响应发出时按声明编码。这样前后端共享的类型有运行时依据。接口 DTO 只暴露明确字段，内部实体和错误堆栈不会直接穿过 HTTP。

## 29. 前端 mutation 为什么有统一包装

**面试官**：为什么还要封装 useApiMutation？

**我**：它解决两类职责分离。

领域失败交给当前页面，例如记录已经被别人修改、当前阶段禁止提交。平台失败集中处理，例如会话过期、限流、服务器故障和前后端版本不兼容。类型层会从页面 onError 中过滤平台失败，页面只看到自己需要穷尽处理的联合。

还有一个关键细节：多请求写流程不会把整段工作交给一次会话恢复。每个 API 请求单独穿过恢复入口。假设第一步创建成功，第二步遇到会话过期，恢复后只重试第二步，避免重复创建。

- packages/web/runtime/src/index.tsx 第 540 到 605 行。

## 30. 浏览器怎样避免带入服务端依赖

**面试官**：前端直接引用契约，会不会把数据库代码打进浏览器？

**我**：契约文件只放 Schema、接口定义和安全错误类型，服务端实现放在独立导出路径。浏览器工程也不提供 Node 类型。

最后还有产物级依赖图检查。它扫描真实 Vite 构建的 chunk，拒绝 PostgreSQL 驱动、Node 内置模块和服务端包进入浏览器。源代码导入检查能抓直接问题，产物检查能抓多层间接依赖。

我曾经遇到过契约引用错误类，错误类所在文件又带入服务端代码的情况。类型检查可以通过，浏览器产物检查会暴露这种边界泄漏。

# 第七幕：数据库、权限和并发

## 31. 事务怎样与 Effect 组合

**面试官**：数据库事务怎样写？

**我**：数据库插件提供 transaction 函数，它接收一个 Effect，把整段程序放进同一数据库事务。实现使用 acquireUseRelease 管理开始、提交或回滚。

如果当前 Fiber 已经带有事务管理器，内层 transaction 会加入外层事务，不再打开第二个连接。业务服务可以自由组合，也不用把连接句柄沿几十层参数传递。

这一点解决过真实问题。过去显式传连接句柄时，某个深层服务忘记转交，就会从连接池读取已提交状态，看不到当前事务刚写入的内容。现在当前事务作为 Fiber 上下文服务传播，事务内调用的查询会自然使用同一连接。

## 32. Promise 中断和数据库连接归还

**面试官**：请求取消以后，正在执行的 SQL 会怎样？

**我**：中断 JavaScript 等待不会自动取消已经交给驱动的 Promise。数据库驱动通常在 Promise 的 finally 中归还连接。如果 Fiber 提前宣布结束，语句仍在后台运行，关闭连接池时可能出现无人等待的借出连接。

查询包装会保存那一个正在运行的 Promise。Fiber 被中断时，它会等待驱动真正结束，再完成自己的中断。数据库会话本身有连接、语句、锁等待和空闲事务超时，进程还有总关闭期限，所以这个等待仍受系统级边界约束。

**现场展示**

- packages/plugins/infra/database/src/server/orm.ts 第 389 到 448 行。

## 33. 多租户隔离怎样保证

**面试官**：tenantId 从哪里来？怎样防止用户改参数访问别的学校？

**我**：普通业务请求不会接收用户自由填写的 tenantId。当前租户来自服务器会话中的 Principal，或者来自已经按会话验证过的服务端关联对象。处理函数从 CurrentUser 取得身份，再传入服务。

数据库查询继续显式带 tenantId 条件，唯一约束和外键也尽量包含租户维度。身份来源、查询条件和数据库约束形成多层防护。

- packages/plugins/base/org/src/server/index.ts 第 1285 到 1290 行。

## 34. 登录中间件为什么能参加类型检查

**面试官**：接口忘记加登录校验怎么办？

**我**：Authenticated 中间件声明自己成功后提供 CurrentUser。接口挂上中间件，处理函数环境里才拥有当前用户服务。处理函数尝试读取 CurrentUser，同时契约没有提供对应中间件时，类型无法闭合。

这能提前发现一类常见失误。运行时仍然会验证会话，类型约束负责确保处理函数与契约声明保持一致。

## 35. 权限为什么要下推到 SQL

**面试官**：权限过滤是在查完数据后做吗？

**我**：列表读取会把组织范围和权限条件写进 SQL。数据库只返回调用者能够看到的数据。

这样既保护数据，也保持分页正确。先查二十条再在内存过滤，当前页可能只剩两条，总数和末页也会错误。Qualy 对时间流使用游标分页，对需要页码、总数和末页跳转的名册使用页码分页，授权范围会参与同一查询。

组织树使用 PostgreSQL ltree 路径。判断目标节点是否位于授权子树，可以写成路径关系并利用索引。

## 36. 为什么写入前检查两次权限

**面试官**：你提到锁内再次确认，讲一下完整顺序。

**我**：我用修改组织节点类型举例。

第一步在事务外快速检查调用者有没有管理目标节点的权力。这样明显无权的请求不会占用结构写锁，也不会通过不同错误探测节点状态。

第二步进入事务，第一条语句锁住该租户的结构行。组织结构、角色范围和人员归属这类相关写入遵守同一锁序。

第三步在锁内重新读取节点并重新检查权限。等待锁期间可能发生节点移动或权限撤销，这次检查才是写入依据。

第四步验证新状态的不变量，例如子节点类型、已有角色授予和人员站位能否继续成立。全部通过后写入，并在同一事务记录审计事实。

**现场展示**

- packages/plugins/base/org/src/server/index.ts 第 314 到 389 行。
- packages/plugins/base/org/src/server/db.ts 第 19 到 33 行。

**面试官**：租户级锁会影响并发吗？

**我**：它会串行化同一学校内低频的结构性写入，这是明确取舍。组织结构和角色授予变化频率较低，错误交错的代价很高。普通读取、填报和审核并不都排在这把锁后面。对于更高频写入，系统使用更细的批次锁、记录锁和乐观指纹。

## 37. 审计、业务历史和监控为什么分开

**面试官**：所有操作都写一张日志表可以吗？

**我**：三类记录承担不同承诺。

审计记录管理和安全事实，例如谁调整了权限。它和业务写入处于同一事务，审计失败时业务写入回滚。

业务历史记录领域对象怎样演进，例如填报版本、审核事件、重新认定和名单变更。它们是业务模型的一部分，会被页面读取和解释。

监控记录性能和故障，用于排查。导出失败不能让学生提交失败，所以它采用尽力发送。三者分开后，保留期、权限、失败策略和查询方式都更清楚。

# 第八幕：综测业务怎样变成可执行系统

## 38. 机制和细则怎样分开

**面试官**：不同学院规则差异很大，你怎样避免大量 if else？

**我**：我先区分稳定机制和变化细则。

稳定机制包括题目版本、填报版本、审核路线、认定、计分方法和分组规则。这些写进代码并由测试保护。

变化细则包括某学院本学期有哪些题、字段怎样填写、需要什么材料、分值和审核路线。它们作为批次中的版本化数据保存。

例如固定分值是一种计算器，求和、取最高和取前几项是几种聚合方式，分组还能设置封顶和保底。学院配置选择这些积木并填参数，底层计算器仍保持少量稳定实现。

## 39. 填报版本为什么追加保存

**面试官**：学生修改材料时直接更新原记录不行吗？

**我**：直接覆盖会让审核依据消失。Qualy 的条目保留稳定身份，每次修改追加一个 revision。审核轮关联自己看到的版本，终局认定也能追溯到对应事实。

这样发生申诉时，可以同时回答三个问题：学生当时提交了什么，审核人员当时认定了什么，计分引擎当时用了哪份冻结计划。

## 40. 审核路线怎样避免过度设计

**面试官**：审核流程是通用工作流引擎吗？

**我**：我把范围限制在综测需要的模型。路线由若干审核级组成，级别可以按组织位置和角色寻找处理人，也可以设置多人表决要求。普通审核沿路线向前，补件、空缺、流程调整、复查和申诉有各自明确状态与事件。

系统没有提供任意节点和任意脚本流转。这个限制让管理员能理解配置，也让服务端能够证明无自审、终点存在、权限范围正确等不变量。

## 41. 审核岗位空缺怎样处理

**面试官**：某一级暂时没人负责怎么办？

**我**：系统会把结构不存在和职位空缺区分开。

参评人的组织路径天然缺少某一级时，解析可以沿冻结路线寻找合法下一步。对应组织存在但岗位没有任命时，审核轮进入 blocked 状态并记录原因。补任命后，巡检会把轮安放到找到的单位并恢复处理。

系统不会悄悄把审批权转给上一级，也不会允许提交人审核自己的材料。这样的保守行为更容易解释和审计。

## 42. 审核、申诉和重新认定怎样区分

**面试官**：结果有争议时直接改分吗？

**我**：系统保留三条含义不同的路径。

普通审核决定当前填报能否通过，并形成终局认定。参评人的申诉针对一个已经形成的不可变结论，打开新的复核轮。工作人员发起的复查也走复核路线。具有独立权限的重新认定可以在严格条件下追加一个新结论，同时终结冲突中的在途复核。

旧认定不会原地更新。历史页面通过前后事实比较，说明结论是维持、更正、撤销或推翻。这样页面展示的是业务效果，审核按钮仍然保持通过和退回等清晰动作。

## 43. 公示为什么做不可变快照

**面试官**：规则或数据之后变化，已经公示的结果怎么办？

**我**：正式公示保存不可变快照。后续申诉或更正通过新业务记录和新的发布结果表达，旧公示保留。

这保证参与者看到的历史页面和当时公开内容一致。重算可以生成新结果，不能让旧链接在后台悄悄变化。

**备注**

- 这一段讲现行模型，不延伸到仍待用户裁决的页面展示政策。
- 当前仍有部分可见范围和入口策略待确认，面试时无需主动引向这些产品决策。

# 第九幕：精确计分与可编程公式

## 44. 小数精度怎样保证

**面试官**：JavaScript 浮点数会不会让分数出错？

**我**：权威计分路径不使用浮点数相加。分值在接口和配置中使用规范十进制字符串，进入引擎后放大一万倍转成 bigint。

例如 3.1250 会转成 31250。比较、求和、封顶和保底都在整数上完成。每一条展示分先按百分位量化，再汇总成展示小计，保证页面上可见行相加等于可见小计。

舍入采用远离零的四舍五入。83.245 显示 83.25，负 0.125 显示负 0.13。这和常用计算器及原有 Excel 习惯一致，学生可以手工复核。

## 45. 求和、取最高和封顶怎样组合

**面试官**：同一题多条材料怎样计算？

**我**：单条材料先由计算器产生精确分值。题目级聚合器再决定多条怎样组合，目前内置求和、取最高和取前 N 项求和。更高一层的分组树处理封顶和保底。

这种分层能表达干部任职只取最高、竞赛取前几项、某大类总分封顶等规则。每层都有独立输入输出，可以单测，也能在结果账页展示每一步。

**现场展示**

- packages/plugins/assessment/core/src/scoring/builtins.ts 第 205 到 245 行。

## 46. 为什么要有认定类型

**面试官**：公式直接读取学生提交的 JSON 不行吗？

**我**：学生提交是陈述，审核后的认定是权威事实。两者需要独立。

系统先用严格 schema 描述可认定字段，例如级别是有限选项，名次是有范围的整数，日期必须落在材料期。题目保存时还会证明学生字段能够安全赋给认定字段，认定字段能够安全赋给公式参数。

公式只接收已经认定的严格参数，不知道学生、材料、数据库或权限。这样公式保持纯计算，审核争议与算术争议也能分开定位。

## 47. 管理员自定义公式怎样保证安全

**面试官**：允许管理员写代码很危险，你怎么做隔离？

**我**：我把编写和运行拆成两个独立进程。

编写沙箱负责源码策略检查、TypeScript 权威类型检查、编辑器诊断和确定性打包。运行沙箱只接收不可变编译产物与 JSON 输入，在 Worker 中使用 QuickJS-WASM 执行。

业务服务通过 Unix Domain Socket 调用它们。沙箱不知道租户、用户、角色、审核和数据库，也拿不到应用环境变量。生产环境中，业务进程不会在本地回退编译或执行管理员源码。沙箱不可用时，相关操作明确失败。

容器层还会限制网络、文件系统和用户权限。QuickJS 继续承担语言执行隔离，独立进程与容器提供额外防线。

**现场展示**

- docs/architecture/formula-runtime.md 的 运行 小节。
- packages/plugins/infra/sandbox/src/index.ts 第 1 到 20 行。
- apps/sandbox-authoring 和 apps/sandbox-runtime 两个应用目录。

## 48. 沙箱输出为什么还要重新校验

**面试官**：沙箱已经隔离了，输出还需要检查吗？

**我**：沙箱输出始终按外部不可信输入处理。业务服务会重新检查长度、JSON 结构、输出 schema、数值范围、ScoreAmount 证明和编译产物哈希。

超时也分两种。软超时表示公式在引擎预算内没有完成，归类为公式执行失败。硬超时表示 Worker 连响应都没有回来，更像运行环境暂时不可用。系统不会把两者都压成零分，也不会把上一次结果冒充本次结果。

## 49. 怎样保证历史公式可重放

**面试官**：公式后来修改了，旧成绩还算得出来吗？

**我**：草稿可以变化，发布版本是不可变事实。题目保存的是具体公式版本身份、契约哈希、运行产物哈希和类型证明信息，不会引用 latest。

运行前会重新核对冻结引用、契约、schema profile 和产物哈希。发现缺失或篡改时，系统把它归类为完整性故障并停止计算。

同一不可变产物与同一规范输入必然得到同一答案。运行层会以产物哈希和输入哈希缓存有限数量的确定性结果。运行环境暂时不可用或超时不会进入结果缓存，因为下一次可能成功。

- packages/plugins/assessment/formula/src/scoring/formula-calculator.ts 第 296 到 376 行。

## 50. 为什么沙箱计算不放在数据库事务里

**面试官**：公式执行和写入怎样保证一致？

**我**：外部进程执行时间不可控，放进数据库事务会长时间持锁。Qualy 采用 prove、lock、settle 的顺序。

先在事务外完成编译或试算，得到带身份的候选。进入事务后锁定相关记录，重新读取版本、哈希和权限，确认候选仍然对应当前事实，再写入。如果期间配置变化，提交会拒绝，调用方重新计算。

这个模式把慢计算移出锁，同时保留写入时的一致性证明。

## 51. 公式能力带来的工程亮点

**面试官**：这套公式系统最难的地方是什么？

**我**：最难的部分是同时守住可表达性、确定性和历史稳定。

只做 eval 很快，真正可用于成绩系统还需要源码策略、严格参数类型、不可变发布、资源预算、沙箱身份、输入输出复核、历史版本兼容和发布前样例验证。任何执行失败都要保留语义，绝对不能静默给零分。

这部分也体现了我对安全域的理解。业务进程拥有身份、权限和数据库，沙箱只拥有纯代码执行，两边通过最小协议交互。

## 53. 日志、指标和链路如何关联

**面试官**：具体收集哪些数据？

**我**：链路用于看一次请求经过哪些服务以及耗时分布。日志带请求身份、trace id、span id 和插件来源。指标记录 HTTP 数量、错误率、耗时，数据库连接池和查询耗时，Node 进程资源，以及少量低基数业务动作。

标签值会限制枚举范围，无法识别的值归到统一类别，避免把用户输入或记录编号变成指标标签。页面诊断使用授权页面编号和路由模板，不上报真实地址里的人员或批次编号。

## 54. 为什么选择标准协议

**面试官**：监控平台绑定某个云厂商吗？

**我**：服务端导出使用 OTLP 标准协议，应用侧只关心端点和认证配置。前端真实用户监控通过插件提供，具体厂商实现可以替换。开发环境未配置导出时，遥测 Layer 会退化为空实现。

项目当前使用 Effect 自带的 OpenTelemetry 导出能力，没有加载完整的官方 Node 自动埋点 SDK。原因是现阶段需要的 span 和指标已经由 Effect 与业务边界产生，引入额外 ESM hook 和第三方自动埋点收益有限。

## 55. 监控挂了会不会影响业务

**面试官**：监控平台不可用时，提交会失败吗？

**我**：监控导出采用尽力策略，批量发送、有限重试，持续失败会退避，业务请求不会等待远端监控。

审计承担不同承诺。权限变更等安全事实与业务写入同事务，审计失败会让写入回滚。刚才那三类记录的失败策略差异，在这里就很重要。

## 57. 为什么切换语言要整页重载

**面试官**：React 应用通常能直接切语言，为什么这里重载？

**我**：Qualy 让一个浏览器文档从创建到关闭固定一种语言。用户切换前会收到未保存数据风险提示，确认后写账户偏好与 cookie，再整页重载。

这样页面消息、接口错误、页面清单、术语和服务端渲染文字共享同一文档语言。另一个已经打开的标签页继续携带自己的 x-qualy-locale，不会因为共享 cookie 变化而突然中英混杂。

代价是切换动作较重，收益是文档内语言一致、服务端分页与排序文字稳定，也减少运行时双语目录和响应式重渲染复杂度。

## 58. UI 平台怎样避免业务插件各做一套

**面试官**：前端组件很多，怎样保持一致？

**我**：业务插件通过 @qualy/ui 使用产品级组件，Mantine 作为内部 widget 基础，StyleX 负责正式样式扩展。页面、布局、插槽和导航都有统一声明。

共享组件修改会影响很大，所以页面级特殊需求通过窄选项开启。例如表格在手机端是否按事实行布局，需要由具体表格明确选择，避免一个全局 nowrap 或省略号规则破坏其他页面。

## 59. 会话和外部登录怎样保护

**面试官**：登录安全做了哪些事？

**我**：会话使用服务器存储和安全 cookie，接口入口检查来源。CAS、OIDC 和 GitHub 等外部登录由独立驱动提供，回调使用 state 等协议保护，OIDC 还要处理 PKCE 和 nonce。

敏感配置通过 secrets 能力或部署环境进入，日志中使用 Redacted。高风险匿名动作接验证码能力，当前产品选择本地工作量证明提供方，另一个云端提供方随产品配置关闭。

浏览器 HTML 由 web 插件提供 CSP、frame 限制和跨源策略。外部登录或验证码需要新增脚本来源时，提供方会贡献对应策略，装配阶段检查冲突。

## 60. 为什么页面隐藏无法代替授权

**面试官**：按钮都隐藏了，还需要服务端重复判断吗？

**我**：页面清单和 capability 只改善体验，让用户少看到无法执行的动作。浏览器内容可以被修改，请求也能手工构造。

每个服务端读写都会重新验证身份、租户、资源和权限。写入在需要时锁定并复核。前端收到 manageable 等字段后决定按钮状态，服务端仍然拥有最终决定权。

## 61. 列表和上传怎样控制资源

**面试官**：怎样防止一个请求拖垮服务？

**我**：列表接口有明确页大小上限。时间流用游标分页，名册类页面用页码分页并返回总数。请求体有全局大小上限，附件先创建受权限控制的上传预留，再流式上传到存储后端。

公式源码、编译产物、沙箱输入输出、事件流连接数和单账户计分次数都有独立预算。超出预算会明确拒绝或降级到重新同步，不会静默截断业务数据。

# 第十二幕：构建、部署和新旧版本共存

## 62. build、deploy、start 怎样分工

**面试官**：这个项目怎样发布？

**我**：我把构建、部署和启动分成三个职责。

构建负责生成不可变镜像与浏览器产物，校验插件集合和前端组件图，不连接生产数据库，也不生成迁移。

部署负责应用已经提交并评审的迁移，把本次 Web release 安装进持久 release store，再启动新颜色实例并完成健康核对。

生产启动只校验锁文件、数据库版本和发布身份，再构建应用。它不会自动解析插件、生成迁移或修复状态。

这个分工让同一个镜像在不同阶段行为可预测。部署失败时保留当前颜色服务，回滚也有明确 release 身份。

## 63. 数据库迁移为什么只增不改

**面试官**：表结构怎么升级？

**我**：整个产品只有 db/migrations 一条迁移历史。开发时通过两个 scratch 数据库比较已提交历史与当前实体目标，生成候选迁移。开发者审阅后提交 SQL。

已提交迁移保持不变，线上问题使用新的修复迁移。每个迁移声明 expand 或 maintenance 类型，带数据变化的迁移需要升级测试。构建不会临时生成迁移，服务启动默认也不会应用迁移。

## 64. Web release 怎样共存

**面试官**：前端静态文件更新后，用户旧标签页怎么办？

**我**：每次前端构建产生不透明 releaseId。浏览器的每个 API 请求携带 releaseId 和客户端协议代次。服务端会判断当前页面能否与本进程继续协作。

同一套插件和同一套浏览器入口，只改内部实现时，保留的旧 release 可以继续使用。插件集合变化、页面入口集合变化或协议不兼容时，服务端返回 409 与专用响应头，前端显示需要刷新。系统不会自动刷新，因为用户可能正在填写长表单。

静态资源按内容哈希长期缓存，不同 release 的资源在 store 中共存。HTML 与公开文件使用 no-cache。服务进程启动时固定自己的 release，运行期间不会跟随指针漂移。

## 65. 为什么需要两个装配指纹

**面试官**：插件集合哈希还不够吗？

**我**：resolutionHash 回答选择了哪些插件及结构贡献。browserContractHash 回答浏览器有哪些页面、布局、插槽和登录方式身份。

同一个插件集合可以新增页面，monorepo 内部插件版本也可能都保持 0.0.0。这时第一个哈希可能不变，旧页面却无法渲染服务端新返回的入口。第二个哈希覆盖浏览器入口集合，可以识别这种变化。

浏览器不会看到这两个哈希，只接收继续使用或需要刷新的结果，减少内部实现泄露。

**现场展示**

- apps/server/src/client-compatibility.ts 第 20 行附近。
- packages/build/web/src/browser-contract.ts 全文。
- docs/architecture/web-release.md 的 服务端兼容检查 小节。

## 66. 蓝绿升级怎样降低停机风险

**面试官**：部署时会停机吗？

**我**：生产采用蓝绿两套应用进程。新颜色装入同一提交的 server、运行沙箱和编写沙箱镜像，先执行部署阶段，再启动并通过 readiness 与公网核对，最后切换流量。旧颜色排空连接后停止。

镜像和 Web release 都有不可变身份，旧静态资源在保留期内继续存在。新颜色任一步失败时，旧颜色仍然提供服务。

我会把这描述成当前发布机制，不会承诺绝对零风险。数据库维护迁移、外部依赖和宿主机故障仍需要独立运维计划。

# 第十三幕：测试和质量门禁

## 67. 怎样验证这么大的项目

**面试官**：测试体系怎么设计？

**我**：我按错误能出现的层次安排验证。

类型检查覆盖服务端、浏览器、测试和 Effect 特有诊断。仓库结构测试检查插件隔离、错误码唯一、接口路径、包导出、国际化消息、迁移纪律和浏览器依赖图。

领域服务和授权测试使用 Node 测试。涉及锁、约束和事务的用例连接真实 PostgreSQL，由统一测试上下文创建隔离数据库。组件和页面使用真实 Chromium，少量兼容性用例再跑 WebKit。生产 smoke 会按正式模式启动镜像，检查健康、静态资源、安全响应头和优雅关闭。

## 68. 为什么数据库测试不用 mock

**面试官**：真实数据库会拖慢测试，为什么不用内存 mock？

**我**：组织树路径、约束名翻译、行锁、事务隔离、延迟约束和迁移升级都依赖 PostgreSQL 语义。mock 可以覆盖纯服务编排，无法证明这些关键性质。

我把纯逻辑测试与数据库测试分开，数据库生命周期由测试上下文统一管理，文件之间可以并行。测试结束还会检查连接是否归还，避免一组通过却让进程收尾卡住。

## 69. 迁移怎样测试

**面试官**：空库能建起来就够了吗？

**我**：还需要升级测试。测试会先构造旧结构和旧数据，运行新迁移，再断言数据、约束和索引符合新语义。

空库验证全历史可重放，升级测试验证真实存量如何变化，实体对照验证迁移完成后的数据库是否等于代码声明。三者回答不同问题。

## 70. 怎样看待覆盖率

**面试官**：覆盖率多少？

**我**：我没有把单一覆盖率百分比作为目标。这个项目更关注不变量是否有可失败的测试，例如同一结论只能消耗一次申诉机会、权限在锁内再次确认、旧 release 与新服务不兼容时会阻断、沙箱超时不会变成零分。

截至 rc.24 的已记录 CI，Node 有 3098 个通过测试，Chromium 有 1605 个通过测试，WebKit 有 50 个通过测试。这个数字只代表当次发布提交的 CI 证据，后续提交仍要重新验证。

**备注**

- 数字来源为 STATUS.md 当前记录。
- 现场可以说 三千多 Node 测试 和 一千六百多 Chromium 测试，减少提交变化带来的尴尬。

# 第十四幕：故障复盘

## 71. 冷缓存出现两份 React

**面试官**：讲一个排查最深入的 bug。

**我**：我讲一个 Vite 冷缓存故障。

现象是浏览器测试在 CI 偶尔出现 invalid hook call，本地热缓存长期无法复现。清掉本地 Vite 依赖缓存后，问题稳定出现，这说明差异来自依赖扫描状态。

插件组件通过虚拟模块中的动态 import 进入应用。Vite 冷启动扫描看不到完整组件树，应用运行到一半才发现新的第三方依赖并触发重新优化。结合 pnpm 的依赖隔离，React 从两个解析位置进入页面，Hook 检查因此失败。

修复分三步。生成 import 统一使用相对路径，减少不同根的解析差异；再生成一份静态 import 的扫描副本，让 Vite 启动前看到全部插件组件依赖；最后把扫描入口和应用根放到正确 workspace 包。CI 保留冷缓存覆盖，避免问题重新被本地缓存掩盖。

**现场展示**

- packages/build/web/src/collect.ts 第 124 到 173 行和第 244 到 260 行。
- packages/build/web/src/vite.ts 第 23 到 74 行。

**我**：这个问题让我形成一个排查习惯。CI 偶发、本地稳定时，先列出两边状态差异，例如缓存、并发、时钟、文件系统和数据库隔离，再通过删除状态把偶发现象变成可重复实验。

## 72. 数据库连接在关闭时卡住

**面试官**：再讲一个后端问题。

**我**：有一次测试主体已经结束，进程却在释放数据库 Layer 时卡住。数据库里能看到连接最后执行了 commit，却长期没有归还。

继续跟踪发现提交本身也可能被数据库拒绝，例如延迟约束在 commit 阶段触发。驱动对象仍挂着事务状态，直接结束 Effect 会让连接留在借出账本里。

修复是在 settle 阶段区分业务结果与提交结果。提交失败后再尝试回滚，让驱动完成连接归还；回滚也失败时把连接标成损坏。数据库借出账本同时记录 Fiber、span 和插件来源，关闭超时时能直接指出持有者。

**现场展示**

- packages/plugins/infra/database/src/server/orm.ts 第 204 到 245 行。
- packages/plugins/infra/database/src/server/checkouts.ts。

## 73. 多请求写入被会话恢复重放

**面试官**：前后端交互里遇到过什么语义 bug？

**我**：一个多步骤写流程先完成第一项写入，第二项请求发现会话过期。早期实现把整段工作放进统一恢复，登录完成后整段重跑，第一项写入会重复。

我把恢复单位改为单个 API 请求。多步骤工作流用 Promise 按顺序组织，每个请求分别通过 useRunApi。成功结果立即更新局部缓存，失败后的状态清理放在 onSettled。这样恢复只重试真正没有完成的请求。

这个例子说明恢复边界会改变写入语义。重试功能只有和幂等性、部分成功与缓存更新一起设计，才能安全。

**现场展示**

- packages/web/runtime/src/index.tsx 第 560 到 605 行。

# 第十五幕：取舍、个人贡献与收尾

## 74. 插件化有没有过度设计

**面试官**：一个高校系统做这么多插件，会不会过度？

**我**：插件化确实增加了描述、解析和组装成本，所以我只让真正存在替换或选择需求的能力成为插件。

登录协议、邮件后端、存储后端、验证码、浏览器监控、布局和计分扩展都存在替换需求。学院细则继续使用数据配置。项目维持单一产品和单一发布物，不做运行时插件市场。

这些约束让插件解决模块关系，同时把产品组合复杂度控制在构建与发布阶段。

## 75. 最大的技术债和局限

**面试官**：项目目前还有哪些不足？

**我**：我会诚实讲三点。

第一，Effect v4 仍处预发布期，升级成本需要持续预算。项目已经有版本锁、上游源码校验和诊断测试，仍然无法消除生态变化风险。

第二，领域模型已经很深，新成员理解审核、认定、申诉和计分需要系统文档与演示数据。下一步可以继续做面向开发者的领域地图和更短的端到端样例。

第三，生产验证目前能证明部署、匿名登录页、静态资源、健康探针和真实浏览器加载。它无法证明多学校真实规模和长期性能阈值。监控阈值需要根据一段真实基线调整。

另外，当前仍有几项页面可见范围和入口策略等待产品裁决。我不会用现有代码反推政策答案。

## 76. 你个人做了什么

**面试官**：这是你一个人做的吗？你的贡献怎么说明？

**我**：Qualy 是我主导设计和实现的项目。我负责业务建模、插件与 Effect 架构、数据库和 API、前端平台、测试门禁、沙箱、发布协议及部署验证。

**我**：我认为是把复杂约束转成可执行系统的能力。

# 分支题库：面试官沿不同兴趣继续追问

下面的问题从主线中的一句回答自然产生。现场只选择对方感兴趣的分支，无需逐题背诵。

## 分支 A：面试官继续追 Effect

### A1. Effect.gen 会不会损失类型推导

**面试官**：生成器写法只是语法糖吗，失败和依赖怎样累积？

**我**：每次 yield* 都取得一个 Effect 的成功值，同时把它的失败类型与依赖类型合并到外层生成器。最终函数签名由 TypeScript 推导。需要对外稳定接口时，我会在 Context.Service 中显式写服务方法签名，让实现与公开契约互相校验。

### A2. 什么时候使用 orDie

**面试官**：把错误变成缺陷会不会掩盖问题？

**我**：orDie 表示当前调用者没有合法恢复动作，这个选择需要在接口语义上成立。示例 ping 接口没有把数据库不可用声明成领域失败，所以数据库写入失败进入统一系统故障。业务拒绝，例如状态冲突和无权访问，会保留在错误通道。数据库约束翻译发生在错误通道中，不能过早 orDie。

### A3. Effect 怎样重试

**面试官**：Effect 自带重试，你会给数据库写入自动重试吗？

**我**：重试策略取决于操作语义。只读请求或明确幂等操作可以在有限条件下重试。普通写入不会因为框架方便就自动重跑，尤其多请求流程会产生部分成功。数据库序列化失败若需要重试，也要让整个事务体重新执行，并确认内部没有外部副作用。

### A4. 并发任务怎样失败

**面试官**：多个 Effect 并发执行，一个失败会怎样？

**我**：并发组合会按照所选算子决定失败和中断策略。应用启动的资源构建需要任何关键项失败就收束整体作用域。业务批量读取可以把每个账户的失败降成行级状态，避免一名学生的计分过大让整页消失。策略写在组合位置，单个服务保持明确失败语义。

### A5. Layer 会不会重复构建服务

**面试官**：同一个服务被多个插件依赖，会建立多份吗？

**我**：Layer 通过 memo map 复用同一构建。组合根还特别保证运行阶段 Layer 使用同一个引用提供给启动屏障和请求路由，避免不同分支先后构建出两份服务。相关行为有 runtime-memo 测试保护。

**现场展示**

- apps/server/src/runtime.ts 第 143 到 154 行。
- apps/server/tests/runtime-memo.test.ts。

### A6. Effect 的学习成本怎样控制

**面试官**：新同事看到这些类型会不会难以上手？

**我**：平台层封装 Context、Layer、HTTP 和数据库细节。业务开发常见形态是 Effect.fn、Effect.gen 和 yield* 服务。仓库提供已裁决模式、示例插件和诊断门禁。代码评审关注服务签名、失败语义和运行入口，避免每个人发明一套组合方式。

## 分支 B：面试官继续追插件和前端构建

### B1. 插件能由第三方提供吗

**面试官**：这个插件系统支持外部包吗？

**我**：装配器按包导出读取描述，技术上可以加载外部包。当前产品定位仍是单一产品，第三方包需要先经过依赖安装、代码审查和产品选择，再重新解析与构建。线上没有动态插件市场。

### B2. 插件配置为什么拒绝未知字段

**面试官**：配置多写一个字段忽略掉不行吗？

**我**：未知字段经常来自拼写错误。sampleRate 写成 sampleRtae 后，如果系统静默使用默认值，部署看似成功，实际行为偏离预期。解析阶段拒绝未知字段，可以把问题定位到插件和字段。

### B3. 动态 import 是否导致很多小 chunk

**面试官**：每个页面动态加载会不会产生大量请求？

**我**：动态加载提供页面级拆分，构建层还会分析真实 chunk 图、静态闭包、压缩体积、小 chunk 数量和环。共享依赖按实际入口关系合并，消息也有独立分组阈值。优化依据是构建产物测量，避免仅凭源码 import 数量猜测。

### B4. 页面地址为什么还要稳定编号

**面试官**：直接用 URL 当页面身份不行吗？

**我**：稳定编号用于插件之间导航、页面清单授权、组件映射和监控分组。URL 可以带参数，也可能因产品设计调整。其他插件只引用页面编号，界面登记能力把编号解析成当前路径，减少跨插件耦合。

### B5. 页面清单会不会很大

**面试官**：每次登录都返回全部页面和菜单，体积怎么控制？

**我**：清单只包含当前用户可见入口和少量文档级上下文，不包含组件源码、模块路径和大业务数据。文档上下文有明确 4 KiB 预算。页面业务数据继续通过各自分页接口获取。

### B6. 前端组件缺失时为什么不直接崩溃

**面试官**：服务端清单和前端包不一致，应该在启动时已经发现吧？

**我**：构建和启动会校验浏览器入口哈希，正常发布应当一致。运行时保留缺失组件状态用于防御旧标签页、损坏缓存和异常部署。它给用户可理解的恢复入口，也给监控稳定诊断信息。

## 分支 C：面试官继续追业务建模

### C1. 批次为什么需要冻结参与者

**面试官**：为什么不每次按当前组织树找学生？

**我**：一次测评持续数周，期间学生可能转班、复学或离校。参与者快照定义这次测评覆盖谁，组织锚点定义审核、排名和授权使用的范围。管理员可以显式检查组织变化并选择同步或保留，系统记录决定，不会在后台悄悄改变历史上下文。

### C2. 审核人换届怎么办

**面试官**：提交以后班长换人，待办给谁？

**我**：路线冻结的是组织级别与角色要求，当前处理人可以根据有效任命解析。职位空缺时轮会阻塞，补任命后恢复。已经发生的审核事件保留原处理人，未来待办交给新的合法持有人。

### C3. 怎样防止自己审自己

**面试官**：提交人本身也是班委呢？

**我**：候选审核人解析会排除参评人本人。排除后无人可处理时，轮进入明确阻塞或按冻结路线继续解析，绝不会让自审发生。

### C4. 申诉为什么限制次数

**面试官**：一个结果可以无限申诉吗？

**我**：每个不可变结论给参评人一次申诉机会。新填报版本形成新结论后会获得新的机会。系统终止、题目作废或人员移出导致的无结论轮不会消耗机会。服务判断与数据库部分唯一索引使用同一谓词。

### C5. 为什么审核决定不直接带分数

**面试官**：审核员已经知道该加几分，直接填分更简单吧？

**我**：直接填分会把事实判断和规则执行混在一起。审核员填写认定，例如级别和名次；计算器根据冻结规则得出分数。规则有误时可以修正规则并保留原认定，认定有误时通过复核追加新结论，责任链更清楚。

### C6. 怎样解释一名学生的最终得分

**面试官**：结果页面能展示到多细？

**我**：账页可以从总分展开到分组、小计、题目和单条认定。每条显示当前 standing、贡献值和拒绝原因。精确量化保证展示行相加等于展示小计。历史还可以追到填报版本、审核轮和公式版本。

## 分支 D：面试官继续追数据库与安全

### D1. 为什么实体用 MikroORM，查询用 Kysely

**面试官**：同时用两个数据工具会不会重复？

**我**：MikroORM 负责实体元数据和目标结构，便于统一生成与检查迁移。业务查询默认用 Kysely，它更直接表达复杂 SQL、分页、锁和 PostgreSQL 特性，同时保留表字段类型。两者通过同一实体闭包和命名策略连接，各自承担擅长部分。

### D2. 为什么不直接写原生 SQL

**面试官**：复杂查询直接写 SQL 更清楚吧？

**我**：PostgreSQL 特有表达会保留成最小 typed fragment，例如 ltree 和锁相关语句。普通筛选、连接、分页和写入交给 Kysely，能让表名字段名参与类型检查。目标是保留 SQL 表达力，同时缩小无类型字符串范围。

### D3. 删除组织节点为什么采用软删除

**面试官**：删除一条组织记录为什么这么复杂？

**我**：历史批次、人员和授权可能长期引用这个单位。物理删除会破坏历史解释。节点离开当前树后保留身份和删除时间，恢复时重新验证父节点与层级规则。删除前还要询问其他插件是否仍有占用。

### D4. 最后一个管理员怎样保护

**面试官**：管理员把自己和其他管理员都删了怎么办？

**我**：角色撤销在同一租户锁内复核剩余管理员，禁止移除最后一个有效管理员。前端可以提前隐藏动作，服务端写入仍执行权威检查。批次内的授权还要区分显式授予、组织继承和 deny 来源。

### D5. 游标为什么带查询指纹

**面试官**：游标不就是最后一条记录的 id 吗？

**我**：游标还要绑定排序锚点、范围和筛选条件。把搜索条件或权限范围变化后继续使用旧游标，会漏数据或重复。Qualy 把查询身份编码进游标，服务端发现游标与当前问题不匹配时明确拒绝。

### D6. 怎样处理跨站请求

**面试官**：cookie 会话怎样防 CSRF？

**我**：API 入口检查请求来源和允许的站点，带请求体的 API 强制声明 JSON Content-Type。会话 cookie 使用安全属性，外部认证回调通过 state、PKCE 和 nonce 等协议状态保护。来源检查先于客户端版本检查，跨站请求无法通过错误差异探测内部协议。

## 分支 E：面试官继续追工程化与性能

### E1. 为什么使用 monorepo

**面试官**：所有包放一个仓库有什么好处？

**我**：接口契约、插件描述、浏览器组件和发布工具会共同变化。单仓库让一次提交能同时更新契约两端、迁移和测试，也能通过 workspace catalog 保证 Effect 等框架只有一个版本实例。代价是全仓门禁更复杂，所以需要 package export、依赖图和插件隔离检查。

### E2. 为什么 Node 直接运行 TypeScript

**面试官**：服务端不先编译吗？

**我**：Node 使用 strip-types 直接运行 workspace TypeScript，减少开发与生产的额外转译层。源码因此遵守可擦除语法约束，相对导入带 .ts 扩展，避免 enum、namespace 和参数属性等需要转换的语法。类型检查仍由独立 tsgo 门禁执行。

### E3. 性能优化怎样做证据

**面试官**：你做过哪些性能优化？

**我**：我会讲有测量依据的三类。浏览器按页面动态分包并检查真实 chunk 图；数据库把授权范围下推并为组织路径和关键分页建立索引；公式纯函数按不可变产物哈希和输入哈希缓存有限结果。

我不会把一次 Lighthouse 分数当作长期结论。性能声明需要说明页面、数据规模、缓存状态和测量环境，生产阈值要等真实基线。

### E4. 开发服务怎样避免重复启动

**面试官**：前后端开发需要起很多进程吗？

**我**：服务端宿主在开发模式下把 Vite 附加到同一个 HTTP 实例，热更新 WebSocket 也使用同一端口。公式沙箱是独立进程，由开发监督流程管理。开发者运行一个入口，监督器负责进程生命周期和日志归属。

### E5. 为什么 releaseId 是随机身份

**面试官**：releaseId 为什么不用时间戳或语义版本？

**我**：浏览器只需要判断相等，无需比较新旧。随机不透明身份避免向公开探针泄露构建时间和提交顺序。私有构建元数据仍保存 revision，供部署和审计使用。

### E6. 如何回滚

**面试官**：新版本有问题怎样回滚？

**我**：蓝绿流量可以切回旧颜色，Web release store 仍保留旧 shell 和哈希资源。数据库迁移遵守前向兼容与扩展优先，回滚应用前先确认旧版本能读取当前结构。破坏性维护迁移需要单独窗口，不能依靠应用回滚自动修复数据库。

# 现场表达边界

## 可以主动强调

- 项目解决高争议成绩的可追溯性，业务问题足够具体。
- 插件描述、Effect 服务、HTTP 契约和浏览器组件都能现场打开代码。
- 权限检查下推 SQL，结构写入锁内复核。
- 计分使用十进制字符串和 bigint，公式运行在独立进程。
- build、deploy、start 职责分离，新旧 Web release 有明确兼容协议。
- 当前 CI 和生产 smoke 有具体证据，同时说明证据覆盖范围。

## 需要注明证据范围

- CI 数量只代表 rc.24 发布提交。
- 公网 smoke 覆盖登录页、静态资源、探针和健康检查，没有在生产数据上执行写入。
- Lighthouse 或本地构建测量属于一次实验，不代表长期生产性能。
- 多租户模型已经存在，真实多学校使用规模没有仓库证据。
- 监控架构已实现，主观阈值仍需真实运行基线。

## 不主动引导的方向

| 方向                   | 现场处理方式                                           |
| ---------------------- | ------------------------------------------------------ |
| 尚待裁决的页面可见范围 | 说明服务端保持保守行为，产品政策需要负责人确认         |
| 真实学校数量和用户规模 | 只陈述可验证部署与测试，不推断客户规模                 |
| Effect 调度器内部算法  | 说明项目使用到的取消、作用域和追踪语义，再回到真实代码 |
| 任意工作流引擎         | 说明路线模型针对综测收敛，强调可验证性                 |
| 运行时插件市场         | 说明插件集合随 release 固定，外部插件需要评审和重建    |
| 绝对零停机承诺         | 说明蓝绿机制和失败回退，同时保留迁移与宿主故障边界     |
| 未经长期测量的性能数字 | 给出测量方法和一次证据范围，避免外推                   |
