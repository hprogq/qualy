# 文档维护

## 文档职责

- `docs/README.md` 是人的阅读入口。
- `AGENTS.md` 是自动化工具的短工作入口，只保留全仓硬约束和任务路由。
- `STATUS.md` 是当前工作、阻塞和已部署版本的短快照，不是会话日志。
- `docs/architecture` 说明当前系统形状；`docs/domain` 指向有效业务规则；`docs/development` 说明日常工作方式。
- `docs/adr` 保存已经作出的决策；`docs/notes` 保存窄证据；`docs/upstream` 保存可独立提交的上游问题。
- `docs/archive` 保存仍有追溯价值、但不再指导当前开发的历史方案。

## 更新规则

1. 先确认读者和权威来源。代码与测试说明现状，ADR 和已接受的领域裁决说明约定。
2. 同一事实保留一个主要出处。其他文档用链接，不复制会漂移的版本、命令清单或配置默认值。
3. 完成的计划要么改写为当前说明，要么进入归档；原始聊天、终端流水账和整份上游手册不长期保存在当前树。
4. 移动文件前搜索代码、脚本、测试和文档引用。归档材料中的历史名称可以保留，现行说明中的路径必须修正。
5. 删除有证据标签、许可证要求或工具消费关系的资料前先确认消费者。`repos`、fixture、运行时资源和生成物不属于文档清理范围。
6. 文档检查至少包括格式、相对链接、标题锚点、资源路径和 `git diff --check`。

## 写作要求

用自然语言解释真实问题、选择、代价和边界。不要把计划写成已经实现，也不要从设计能力推断真实使用规模。保留失败尝试中能解释当前代码的部分；单纯重复 Git 历史的聊天和流水账可以删除。
