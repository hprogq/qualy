# ADR 0012：页面装配移到服务端，采用 React Router RSC Data Mode

- 状态：**已接受，迁移进行中**（2026-11-08，阶段 2 已验收；分支已切换默认构建与宿主并清理 SPA 启动、装配和路由适配；双版本发布与性能对照待完成；证据见文末）
- 相关：[浏览器公开面](../architecture/browser-surface.md)、[Web Release 协议](../architecture/web-release.md)、[ADR 0010](0010-ui-widget-platform.md)、[ADR 0011](0011-i18n-paraglide.md)、[Web 性能记录](../notes/web-performance.md)

## 背景

浏览器打开任何页面都要先自己发现产品结构：入口脚本取 `/api/app/manifest`，再按 manifest 拉布局与页面 chunk，再拉布局声明的 slot，页面挂载后才开始自己的查询。布局合并、slot 提前预取已经压掉了几段等待，但装配仍发生在浏览器，节流对照下 React 首次提交约 5.5 s、LCP 约 6.2 s。

服务端本来就掌握身份、租户、插件贡献和授权投影。让它在同一个请求里选好布局、页面和 slot，再把带正文的 HTML 交给浏览器，比浏览器重走一遍发现过程更直接。

框架选型已经结束：Next.js 要求文件路由，Waku 会替换 React Router，TanStack Start 的 RSC 仍是客户端主导组合。React Router 8.5 的 RSC Data Mode 接受运行时生成的路由配置，可以嵌入 Qualy 自己的宿主，插件描述器能直接成为路由输入，不需要第二套页面体系。

## 决定

**范围：** 迁移的是 Web 展示层的页面装配。Effect 业务后端、HttpApi 契约、插件描述器和 TanStack Query 都保留。

1. **描述器语义不变。** `Ui.page`、`Ui.layout`、`Ui.slot` 和登录渲染器的声明形状不变，不增加 `server: true` 一类字段。路由 id 直接使用 surface 身份（`surfaceLabel`）。
2. **`'use client'` 划定客户端边界。** 它是 React 的模块图机制：被客户端模块导入的依赖也在客户端执行，同一个无环境依赖的模块可以同时进入两个模块图。因此不能用「是否写了指令」推断整个 surface 在哪里执行，也不能把「加了指令」当成「已兼容 SSR」。
3. **完整的 surface 实现表只在 RSC 环境。** collector 一次收集，按环境输出：RSC 环境得到 surface → loader 表；浏览器只得到 `browserPlugins`。
4. **浏览器只接收组件引用。** RSC 按本次请求加载当前页面需要的布局、slot、动态 renderer 和登录 renderer，交付框架生成的 Client Reference；客户端再把它们适配成 `PluginSurface`、`UiSlot` 使用的运行时 registry。loader、闭包、服务端组件函数都不跨边界。引用集合按「当前页面需要」裁剪，不按「用户有权访问」：交付即披露。登录 renderer 依据当前租户下的登录方式投影选取，不向匿名访客交付全部已安装的登录实现。
5. **授权 manifest 与本次引用是同一份渲染快照，**随 RSC 结果一起更新。RSC 路径不再用一条独立的 manifest Query 去单独替换快照。服务端 QueryClient 按请求新建；浏览器的 QueryClient 在 RSC 导航之间保持稳定。
6. **请求上下文显式传递。** locale 的优先级是：文档 locale 头 → cookie → Accept-Language → 默认。RSC 和 SSR 是两个模块环境，各自建立请求级 scope，locale 作为显式输入从 RSC 传给 SSR，不通过全局单例拼接。首次文档请求的 release 取自本次构建身份。
7. **`Effect.run*` 只在渲染接入处。** 由统一的请求级适配执行；页面通过同一份 HttpApi 契约读取数据，不直接访问 repo 或其他插件的内部服务。第一版走网络 transport。取消、追踪和资源释放覆盖整条响应流，直到流结束、失败或被取消。
8. **错误分类。** 位于 Suspense 边界内的 Client Component 在 HTML SSR 中出错，可以降级为客户端渲染；RSC 执行、模块解析、props 序列化、认证和公共上下文中的错误不算可接受的降级。
9. **Server Functions 当前关闭。** 运行时不传 `decodeAction`、`decodeReply`、`loadServerAction`；渲染入口只接受 GET 和 HEAD；静态门禁拦截 `'use server'`。这是当前政策，不是永久架构原则；将来开放需要另立 ADR，说明它如何登记到插件描述器、如何遵守错误码和审计规则。
10. **服务端可执行产物随镜像固定。** release store 继续保存带哈希的客户端资源，供旧标签页使用；服务器不从可变目录加载可执行代码。

**非目标：** 进程内 transport、Effect Atom、偏好存储重做，以及 SPA 与 RSC 长期并行的双模式。迁移期间原 SPA 入口保留，只用于对照和回退；全部入口验证通过后，切换默认入口，并在同一个变更里删除被替代的启动链。

## 实施阶段

0. 文档身份一致性：在现有 SPA 上独立完成，不依赖本 ADR。
1. 最小插件切片：真实产品组合下的登录页、AppShell 页面加跨插件 slot、`GrantOrigin` 所在页面；验证三个构建环境、引用传递、消息与主题、开发体验和生产构建。
2. 批次概览与平台行为：首屏预取、水合，以及会话、版本、语言的恢复，时区和主题兼容。
3. 全部入口切换与发布验收：其余页面做必要的 SSR 兼容，切换默认入口，删除旧启动链，验证双版本发布和性能。

**止损条件：** 只有修改 React Router 或 plugin-rsc 的内部协议、维护私有补丁、自行解析 Flight、为热更新自造大型协调器，或者必须向浏览器公开完整实现表，才能继续时，就停止，并在下文写明阻点。

## 阶段 1 结论

**结论：带限制通过（2026-11-06，分支 `spike/rsc-data-mode`）。** 真实产品组合的贡献已经在 RSC 环境完成授权装配。全程只使用公开接口：plugin-rsc 的三个入口和按环境配置，React Router 的 `matchRSCServerRequest`、`routeRSCServerRequest` 和 `shouldRevalidate`，Vite 的 `applyToEnvironment`。没有修改框架内部协议，没有自行解析 Flight，也没有维护私有补丁。原 SPA 的聚合模块逐字节不变，SPA 构建通过分包和预算门禁。

### 已证实

- **登录页。** 服务端在同一个请求里，以访客身份读取登录方式和会话状态，并且只交付这些方式用到的登录 renderer。首屏 HTML 里有租户名、主登录方式、其他方式和共享设备选项，不再是等待骨架。水合后复选框和切换登录方式都正常，邮箱表单可以输入；切换后客户端状态保留。
- **AppShell 和 AccountShell 页面。** 布局、顶栏、侧边导航、跨插件 slot（auth 插件的 `account-header`、用户菜单）和页面标题都在服务端 HTML 里。水合后，客户端 Query 正常加载列表。
- **消息。** HTML 渲染阶段按请求 locale 输出中文或英文。生产 handler 按 `Accept-Language` 选择了 en-US。
- **生产构建。** 三个环境都能构建，输出在 `apps/web/dist-rsc/`。生产 handler 可以用 Node 的 `Request` 直接调用：`/login` 返回 200，正文完整；`.rsc` 返回 Flight；POST 返回 405。
- **最小披露。** 匿名文档只交付 7 个 surface 引用：布局、登录页、本地登录 renderer，以及 manifest 对匿名访客开放的抽屉和用户菜单 slot。HTML 里没有插件源码路径。
- **错误分类。** 客户端组件只在 SSR 时抛错，会由 HTML 渲染器记录，浏览器改为客户端渲染，页面可以继续使用。把函数当作 props 跨边界传递，服务端返回 500。平台组件在渲染阶段读取 `window`，整页失败。三种情况的结果都符合分类。
- **取消。** 读者中断请求后，渲染发出的读取请求随 Effect fiber 一起中断，不记为失败，服务端随后正常响应。
- **开发体验。** 编辑客户端组件后热更新正常，输入保留，没有整页刷新。RSC 开发服务是独立进程，后端重启不影响它。

### 限制与阶段 2 的输入

1. **服务端模块的热更新没有接通。** plugin-rsc 会发出 `rsc:update`，接到 `useRevalidator` 之后也会发出重新验证请求并返回 200，服务端单独请求新文档时也已经是修改后的内容，但已经水合的页面没有显示新内容。在时间盒内没有查明原因，相关代码没有保留。
2. **只改 search 的导航不在服务端重新渲染页面**（`pageRevalidation`）。原本由服务端重新渲染时，登录页的分步视图停在了旧视图上，原因同样没有查明。现在的规则和离开确认一致，都只以 pathname 为准。
3. **StyleX 不进入 rsc 环境。** 客户端模块在 rsc 环境里被替换成引用之前，StyleX 已经读过它，于是汇总 CSS 时找不到它引用的常量。因此目前服务端组件不能使用 StyleX 样式。
4. **引用集合目前是"授权的全部 slot 条目"。** 管理员的每份文档要交付 22 个引用，其中包括 `/account/roles` 用不到的公式计算器编辑器。页面不声明自己使用的 slot。建议仿照 `Ui.layout({ slots })` 讨论页面级的 slot 声明。
5. **`GrantOrigin` 没有被开发数据触发。** 两种宿主下结果一致：没有带范围来源的任职记录。grant presenter 的引用已经交付；"客户端在服务端交付的引用里局部选择 renderer"这一机制，已由登录 renderer 验证。
6. **在 SSR 里出现 React 告警** "multiple renderers concurrently rendering the same context provider"，原因待查。
7. **还没做的事项：**
   - CSP nonce 和响应头；
   - 会话清理时的 `Set-Cookie` 透传（`readApi` 目前丢弃所有响应头）；
   - 时区；
   - 暗色和 system 主题的水合；
   - `onManifestMismatch` 和 `useBlocker` 的探针；
   - Effect 宿主挂载：独立 handler 已经通过，嵌入 Effect 宿主留待阶段 2；
   - 生产构建的不透明文件名、分包和预算；
   - 服务端渲染错误按 surface 和请求关联。
8. **web-rsc 的类型。** 服务端模块需要 Node 类型，目前用 `/// <reference types="node" />` 进入插件的浏览器 tsconfig 程序。插件服务端页面的类型检查边界还需要决定。

## 阶段 2 验收（2026-11-07）

生产 RSC 构建挂载到本地 Effect HTTP 宿主。验收脚本使用独立临时库，由业务 API 创建批次和限定在该批次内的任职，再用 Chromium 检查 HTML、Flight 和水合后的交互。

- **首屏。** 批次列表和概览的业务正文、已授权的工作区导航和用户入口都能在脚本接管前显示。概览的直达筛选和分页地址使用对应的首屏数据，水合后不会立即重复读取，批次实时更新照常工作。
- **引用。** 文档先交付当前布局声明且获准的 slot。个人角色与人员任职页根据首屏实际记录交付对应的 renderer。角色编辑页的持有人只在切换标签后读取，因此该页走按需路径。验收中的批次 renderer 随任职页到达，组织选择器在打开授权对话框时才获取。按需请求经过文档身份、版本和当前授权检查，文档采用新授权投影时清理过期缓存。
- **平台行为。** 文档、Flight 和按需引用都使用私有响应。会话清理、CSP nonce、语言固定和拒绝恢复通过生产产物验收。离开确认共用原来的守卫与确认框，RSC 导航由 React Router 的 `useBlocker` 管理。跨标签页换号会冻结旧文档并关闭已有实时连接，拿旧文档身份重连也会在订阅前被拒绝。
- **开发热更新。** 在 Qualy 的开发构建上，修改登录页的服务端依赖触发 `rsc:update`，经 `useRevalidator` 更新页面。探针验证了同一个输入框仍在且草稿保留。测试覆盖这一条真实路由，其余页面的热更新与冷启动耗时需要分别评估。

生产构建探针覆盖 [RSC 验收脚本](../../tools/quality/rsc-acceptance.ts) 中记录的入口。全入口切换、删除旧启动链以及双版本发布验收属于阶段 3。

## 阶段 3：入口与产物准备（2026-11-07）

**入口基线通过，默认入口尚未切换。** 生产构建验收扩展到 190 项，全部通过。页面检查从各身份的授权 manifest 取入口，并与同一装配的 collector 声明核对，避免宿主维护第二份业务页面清单，也避免漏测没有进入这些身份投影的已启用页面。当前组合的 42 个页面均被覆盖；未启用的 demo 插件不进入检查集合。

- 匿名、管理员和参评人分别在 1440px 与 390px 下打开每个获准入口。检查实际路由匹配、私有缓存头、SSR 错误标记、浏览器异常、水合错误和平台拒绝屏。模板详情与审核详情没有对应业务记录，目前只覆盖记录不存在的状态；公式编辑器使用经 API 新建的空白草稿。这里的通过不等于这三类页面的完整业务流程已经验收，也不等于所有页面都已预取正文。
- 审核工作台的媒体查询改为复用 UI 层的 `useSyncExternalStore` 订阅：服务端与水合首帧使用相同快照，随后读取浏览器的视口和指针。媒体查询水合、宽度切换，以及既有审核队列和认定回归通过。
- RSC 的客户端 chunk、CSS、字体和 worker 使用现行不透明文件名。StyleX 编译规则进入 `s-*.css` 文档样式表；脚本不带 sourcemap 引用。服务端两个环境的产物仍保留在私有构建目录，公共输出与生产 store 的安装隔离还需在下项验证。
- 邮件链接继续用 fragment 携带 token，生产浏览器验证 token 不进入文档请求和 HTML。有效链接的核销与一次性使用由既有邮件流程测试负责；页面渲染不执行写操作，见[认证安全记录](../notes/auth-security.md)。

下一项是把渲染器、客户端资源与 release metadata 接入正式构建和 Effect 宿主：可执行产物随镜像固定，历史哈希资源保留在 store；然后在一个完整切换变更中改默认入口并删除被替代的 SPA 启动职责。双版本安装、回滚、公开面完整门禁和同条件性能对照尚未完成，不能把本节的本地验收视为发布就绪。

## 阶段 3 修正：页面直接使用服务端组件（2026-11-07）

这一节修正大规模推广页面之前的实现边界。目的是让页面直接用服务端组件组合内容，不再一律采用"原客户端页面加一个预取伴随文件"的写法。

- **服务端组件不需要指令。** `'use server'` 声明的是 Server Function，与服务端渲染无关，本 ADR 仍然关闭它。一个模块只要从 RSC 模块图进入、不写 `'use client'`、也不依赖浏览器能力，就是服务端组件。`*.server.tsx` 只是条件导出选中的文件名，后缀本身没有语义。
- **数据归谁管，就由谁来读。**
  - 只在服务端显示的内容，由服务端组件直接 `await readApiExit()`，然后作为元素交给客户端组件，不经过 Query。
  - 之后仍由客户端 Query 管理的区域，比如实时刷新和分页，由服务端组件把本次读到的结果放进局部的 `QueryHydration`。
  - `prefetch` 不是页面必须导出的东西。它只用于结果需要放在文档根部、交给多个 surface 共用的情况，例如工作区外壳。
- **批次工作区的公共读取由 assessment 插件的 slot 负责。**
  - 上下文栏读取批次、阶段和权限；审核角标读取"我的待办"；管理提醒点读取三项提醒。它们都是插件自己的 slot 服务端入口，宿主和 `web-rsc` 里没有任何业务路径。
  - 工作区权限取自任一 surface 的准备结果，不再依赖当前打开的是哪个页面。
  - 同一请求中，同一个 key 的读取只发一次（`readApiExit` 的 `key` 选项）。
- **示例页：批次概览。**
  - 批次说明由服务端组件从 markdown 画出：渲染器和解析器不交付给浏览器，样式由 RSC 环境编译的 StyleX 提供。客户端只在当前批次的说明与画出时的文字一致时才使用这份结果，说明变了就自己重画。
  - 待办和动态仍由 Query 管理，由页面内的局部水合交接。
  - 文档根部只等待工作区准备，页面自己的读取不再参与根部等待。
- **StyleX 进入 RSC 环境。** 在 RSC 环境里只编译服务端模块，跳过以 `'use client'` 开头的模块（客户端模块由客户端和 SSR 环境编译）。生产构建验证：只在服务端组件里声明的规则进入了文档样式表，HTML 中的类名生效，水合后没有差异。
- **查询参数是否触发重新验证，按数据归属决定。** 现行的全局规则是"只改 search 不重新验证"，它只适用于外壳和由 Query 管理查询参数的页面，不能作为长期的统一规则。第一个由服务端读取并持有查询参数数据的页面，要连同下面的机制和验收一起实现：通过路由的 `lazy`，由页面服务端模块声明自己持有查询，持有查询的页面改用默认的重新验证。另外，数据是否需要重新读取，与是否触发离开确认，是两个独立的问题。
- **登录页不再整表交付登录 renderer。** 读不到登录方式时，服务端不交付任何 renderer；页面请求服务端重绘，失败时显示不可用状态，可以重试。
- **服务端读取的结果分类按状态码判断。** 契约没有声明的状态，typed client 报为 `DecodeError`，而不是 `StatusCodeError`。所有 5xx 都算"无法询问"，由页面在浏览器里重新读取；2xx 却无法解码，按契约不一致处理。

## 阶段 3：默认入口切换（2026-11-07）

分支上的 `pnpm build`、Dockerfile、开发服务和 `@qualy/plugin-web` 生产宿主已改用 RSC 构建。

- **构建产物分两半。** 浏览器一半照旧装进 release store：资源共享、按保留策略回收，release 自己的目录只剩公共文件和元数据，不再有 shell。服务端一半是 RSC 与 SSR 两个环境的产物，由 staging 放到 `@qualy/plugin-web` 的 `server-dist`，随镜像固定，不从 store 读取；它带 `.qualy-server-build.json` 写明自己绘制哪个 release。两个服务端环境在构建时打包全部依赖，产物在没有 `node_modules` 的目录里能独立加载，镜像只需拷贝这个目录。
- **浏览器契约。** RSC 构建的客户端环境写出与原 SPA 相同格式的 surface map，store 据此计算 `browserContractHash`；旧标签页判定规则不变。只做 re-export 的模块（四个 shell 的聚合模块）按它导出的模块定位所在 chunk。
- **宿主。** 启动时核对 pinned release 与 `server-dist` 的 release 一致，否则拒启。`/assets/*` 和 release 的公共文件仍由文件服务处理；其余请求交给渲染器，每个响应生成独立 nonce，CSP 由 `ShellPolicyHeader.forDocument(nonce)` 用冻结后的插件贡献组合，并附加 frame、COOP、Reporting 等文档头。渲染器读取 API 的地址由宿主按请求传入（本进程端口的 loopback），不再依赖环境变量。隐藏路径仍然 404，唯一例外是 React Router 的路由清单请求 `/.manifest`。
- **资源命名。** 服务端两个环境与客户端使用同一套 `a-[hash]` 资源命名，文档预加载的字体名称因此就是 store 里同一字节的文件名。
- **开发服务** 运行 `vite.rsc.config.ts`（`appType: 'custom'`），并把开发后端的地址交给渲染器；监视器在该配置变化时重启 Web 服务。

**验证：** 本地生产构建经 `pnpm build` 装入 store 并通过 `check-staged-web`、chunk、CSP 和公开面门禁；真实的 `run.ts production` 在临时库上启动，登录、批次列表、参评名单、我的申报和审核工作台由宿主直接渲染，水合前后版式一致（只剩计时文字在走）。RSC 验收脚本仍使用自己的宿主挂载同一构建。

**未完成：** 双版本安装与回滚验收；同条件性能对照。（SPA 入口的删除见下文。）

## 阶段 3：HTML 不再等最慢的读取（2026-11-08）

切换后，页面服务端入口在返回前等全部读取完成，而 `Surface` 外层没有 Suspense 边界，所以整份文档都在等最慢的那个读取（参评名单约 2 秒），站内跳转也表现为"按下后停住，再突然出现"。

- **读取只等一小段时间。** `answersOf` 最多等 `HTML_WAIT_MS`（120ms）。这段时间内有结果的读取照旧进入 HTML；没有结果的，以 Promise 的形式随同一个响应送到浏览器（`Handed.coming`）。依赖前一个结果才能决定的读取（名单的总分取决于这一页有哪些人，参评人的申报取决于是否对读者开放），用 `within` 判断前一个结果是否及时：及时就一起读，不及时就留给页面自己读。
- **浏览器把送来的读取当作页面自己的读取。** `QueryHydration` 在页面渲染之前，用 `initialPromise` 让对应的查询进入"读取中"状态。页面照常显示自己的等待态（骨架、spinner），挂载时不会再发同样的请求，结果到达后落在页面读取的 key 下。服务端没有替页面拿到结果的（会话失效、5xx、程序缺陷），到达时改由页面自己的 `queryFn` 去读，程序缺陷同时写进服务端日志。
- **结果要等文档接管之后才落地。** 某个组件渲染时结果是否已经到达，取决于时序（服务端和浏览器都可能在代码加载后才继续渲染某一部分），这会让 HTML 和水合首帧不一致。所以送来的读取一律等文档在浏览器里接管之后才落地，HTML 和首帧都把它画成"读取中"。
- **Flight 传来的是 thenable，不是 Promise。** 它的 `then` 不返回新的 Promise，必须先用 `Promise.resolve` 收编（TanStack 自己的水合也是这样做的）。否则 `initialPromise` 实际为空，查询会改走 `queryFn`，浏览器重复读取。
- **为什么没有改用 Suspense fallback。** 用页面本身做 fallback，会在 fallback 期间发出请求、建立实时连接；每页另写骨架，会和页面已有的等待态重复，而且两者会走样。页面本来就会画"读取中"，把读取交给它是代价最小、和 SPA 行为最接近的做法。
- **服务端入口扩展到**：阶段安排、人员权限、项目配置（assessment），人员名单（auth），组织结构（org），角色（rbac），审计日志（audit），公式库与公式模板（formula）。页面和服务端用同一个纯函数从地址算出查询参数（`access-place.ts`、`users-place.ts`、`events-place.ts`、`list-place.ts`），保证 key 一致。
- **外壳的滚动区域声明为 size 容器。** 粘性填充（参评名单的单位树）在 HTML 里按 `100cqh` 取得粘住后的高度，不再只有内容那么高；水合后 JS 再按滚动位置精确调整，页面顶部时下沿会上移约一个标题栏的高度，这段差异发生在可视区域之外。

**验证：** 把等待时间临时设为 0，让所有读取都走送达路径，在开发服务上检查参评名单、参评人详情、概览、我的申报、我的成绩和审核收件箱：没有水合错误，送来的读取没有被浏览器重复请求。新增的服务端入口逐页核对：正文在 HTML 里，加载后没有重复读取。

**仍然存在：** 实时通道每次连上时会发送 `sync`，部分页面据此把自己的读取全部标记为过期，用来补上断线期间漏掉的事件，所以首次连接后这些页面仍会再读一次。这是既有设计，与服务端绘制无关，暂不改。

## 阶段 3：删除 SPA 入口（2026-11-08）

- **首屏预算改为针对服务端绘制的文档。** `qualyChunkGraph` 挂到 RSC 构建的客户端环境上，并新增 `hostModules`：文档自己的客户端组件（`Document.tsx`、`frames.tsx`）计入每个屏幕。屏幕只计入页面实际使用的那一个布局，而 SPA 当年要等 manifest 里列出的所有布局。分包规则搬进 `apps/web/chunk-pools.ts`，RSC 构建与原 SPA 构建采用同一套规则。实测基线（JS 请求数 / Brotli 字节）：登录 61 / 390345，批次列表 85 / 449342，批次概览 83 / 434414，我的申报 113 / 526976，组织结构 75 / 421652。请求数与 SPA 基线相差在 4 以内，字节多 7–10%，多出的是服务端绘制所需的路由和 Flight 客户端。入口 70184、启动闭包 217321（SPA 为 262370）。预算按 ADR 0011 的规则定在 `apps/web/document-budget.ts`。没有分包规则时，同样的屏幕要 81–175 个请求。
- **删除的文件：** `index.html`、`src/main.tsx`、`src/App.tsx`、`src/shell-style.ts`、`vite.config.ts`、`performance-budget.ts`、`tools/quality/measure-web-chunks.ts`，以及构建插件 `qualyBootFrame` / `qualyShellStyle` 和只为它们存在的测试。
- **CSP：** `script-src` 不再含 SPA 启动脚本的 hash，只有 `'self'`，加上每个文档自己的 nonce。
- **开发服务的文件读取范围：** 原有测试守的是已经不用的 SPA 配置。改为测 `vite.rsc.config.ts` 后发现 RSC 配置缺少 deny 列表（数据库 dump、证书、`.env`），已补上。
- **维护页：** 测试改为让维护页的脚本在模拟浏览器里运行，核对它选出的语言与服务端 `localeOfRequest` 一致，不再与已删除的 `index.html` 逐字比较。
- **CI：** `check-csp-build` 改读 `dist-rsc/client/assets`。`pnpm build` 只产出 RSC 构建后，它读的旧目录已经不存在。

## RSC runtime 收敛与路由错误边界（2026-11-08）

**删除已被替代的职责。** 浏览器不再保留 manifest 启动查询、`RuntimeLoader`、manifest 路由装配、`HistoryRouter` 与自定义 history 补偿。`ColdStart`、wordmark 交接动画及无消费者的页面预取 hook 一并删除。页面局部的 `PageLoading`、Skeleton 和导航进度继续保留，它们表达的是实际等待状态。私有构建聚合模块仍供测试检查描述器使用，没有为清理而删除有效消费者。

**一个文档只采用成对到达的授权投影与 surface。** `RuntimeProvider` 必须接收服务端 manifest，普通 RSC 导航复用 QueryClient；权限变更后的 `useManifestRefresh` 通过 Router 重新验证，不再让一个无人观察的旧 manifest Query 独立失效。登录、退出等明确身份转换创建新文档，并先取消旧查询、冻结实时连接。后台探测只判断会话恢复，不独立替换文档投影。

**错误边界使用现有产品状态。** 根路由、布局和页面分别设置公开的 Router `ErrorBoundary`。根路由通过 `Layout` 共用 HTML、nonce、主题、字体和发布恢复层；页面错误保留可用的外壳。实际 transport 拒绝用独立错误类型表达，普通渲染 `TypeError` 不冒充网络故障。界面复用 `Failure`、`ResourceState` 和现有消息，不显示框架堆栈与实现路径。重试以 replace 导航同一地址，保留 state 和滚动位置；测试同时覆盖慢请求与立即成功的重试，避免错误边界因批量更新而不复位。身份、会话和版本拒绝仍在 transport 进入既有恢复流程，不能落进普通错误页卸载编辑器。

**整理模块，而不建立新兼容层。** runtime 按 `data`、`routing`、`session`、`surfaces`、`document`、`feedback` 和 `live` 分目录，包公开子路径保持稳定。`index.tsx` 从 1131 行收为导出入口；`RailShell` 的样式拆出，保留布局组件；`spinner` 只保留有效加载组件。浏览器 testkit 改用 Data Router 和显式新文档切换，与产品执行路径一致；原有会话、历史导航和离开确认用例随之迁移。

**构建代价与限制。** 按依赖方向归组 API 基础、文档基础组件、Query 和 Motion，保留原预算并检查 chunk 环。生产构建的 JS 请求数 / Brotli 字节为：登录 63 / 390657、批次列表 89 / 452258、批次概览 87 / 435892、我的申报 116 / 527512、组织结构 78 / 421854。各场景均在既有预算内，chunk 环为零；启动闭包为 236720 字节，相对上一节基线增加约 19 KB。这是构建图证据，不能据此宣称首屏更快。真实双版本与性能对照仍未完成。

验证使用隔离测试库与本地生产构建，不读取开发库：

- `pnpm typecheck` 与本轮改动文件的 type-aware lint、oxfmt 通过。
- runtime、RSC 与测试分层门禁的 Node 回归 146 项通过。
- Chromium 完整运行 140 个文件、1811 项中 1810 项通过，阶段排期的连续键盘时间输入出现一次失败；该用例单独运行和所在的 138 项批次管理套件随后均通过，保留并行运行时序不稳定这一限制。前一轮的两个空首页失败来自 testkit 的 index 路由配置，修正后 6 项路由状态测试及完整复跑中的该文件均通过，没有放宽断言。

## 参评人详情的加载与切换（2026-11-08）

参评名单与详情仍是同一个插件页面，`participant` 是该页的地址状态。详情接管批次导航的列，使用同一份 `ParticipantAccountLayout` 绘制正常内容与等待轮廓；`data-screen-aside` 在首段 HTML 中就存在，布局不依赖水合后的注册。窄屏等待态也保留人物头部。`BatchScreen` 的 `bare` / `none` 分支共用组件树，并沿用 `fill` 的高度约束，避免进入详情时重新挂载整个页面而丢失 Drill 过渡。

服务端先在现有 `HTML_WAIT_MS` 内等待准备结果：快速读取直接输出正文，超时才使用局部 Suspense 轮廓。等待组件只负责呈现，不启动 Query 或实时订阅；不能无条件增加 Suspense 边界，让原本能够首屏直出的内容也退成依赖脚本替换的骨架。`within` 复用同一个有界等待实现，结果类型不再限于 Effect Exit。

已经打开的详情换人时，当前人的姓名、操作和正文保留成一组；既有 Query 先读取目标人物、成绩及其允许查看的申报，被选择的名单项或前后按钮给出等待反馈。准备完成后一次更新地址与正文。缓存中新鲜的目标可以立即使用；查询的新鲜期与挂载后的消费者一致，实时事件和写入继续使原 key 失效。新的选择覆盖旧的选择，历史导航清除待切换意图，迟到结果不能重新打开它。这里没有把上一人的成绩作为下一人的 placeholder。

回归覆盖慢申报、连续选择、后退再前进与重复读取计数。生产验收通过测试宿主为人物 API 注入延迟，再检查第一段真实 HTML，以及禁用脚本的桌面和手机布局；故障注入的 Effect 定时 API 依据 `repos/effect/packages/effect/src/Effect.ts` 的 `sleep` 定义（4924 行）。这一故障入口只存在于验收脚本。

## 水合与加载反馈收敛（2026-11-08）

登录页的最近登录方式改为有界 cookie 偏好，服务端随页面传入，水合首帧采用同一值；它只匹配当前提供的方法，不携带账号或认证信息。停止读取旧 localStorage 记录，不增加启动迁移或自动刷新。已有登录页在水合时直接可见，登录方式之间的局部 Motion 过渡保留；水合失败引起的重建不能当作入场动画。

React Router 8.5 的 RSC 包装会在路由更新时更换 router 对象，`useBlocker` 的两个 effect 因此可能重新注册旧 key。在既有离开适配层中，仅把注册控制组件绑定到公开 `useNavigate` 句柄的生命周期；决策、确认框和编辑器保留。真实开发导航与重复包装的浏览器回归检查单个 blocker、草稿节点以及保存后离开，没有修改框架内部状态或过滤警告。服务端 Context 同时改为模块图内持有，只有浏览器为 HMR 保留稳定引用，避免多个服务端 renderer 共享进程全局 provider。

参评名单及工作区不再整块淡入；名单与详情的 Drill 过渡保留。慢服务端读取输出带标题和行骨架的只读轮廓，客户端列表等待复用同一份行骨架；分数到达只更新单元格，不重新挂载列表。顶部进度表达导航，骨架表达尚无正文的数据区域，局部 spinner 表达具体操作，三者不再依次接管同一块名单。批次列表不额外叠加入场效果，保留首屏直出、卡片切换和展开反馈。

字体通过独立 Server Component 的 CSS import 交给框架管理，使用 `@qualy/ui/fonts.css` 访问 UI 包拥有的 Fontsource 依赖；宿主不直接导入其传递依赖。删除手写的内联 `@font-face` 和 `optional` 副本，保留 Fontsource 的外部字体文件与标准声明。文档提前请求同一份 Latin 资源，开发与生产均复用正常资源 URL。开发服务的 `no-cache` 会触发重新校验，实测暖缓存请求返回 304，不等于重新下载字体；即使文件已经缓存，等到晚到的 CSS 才发现字体仍可能先排版回退字体。暖访问的逐帧标题宽度和 font 检查同时约束资源发现与水合交接，而非只确认请求成功。

StyleX 开发态使用上游自带的完整更新 runtime，在水合后接管首屏链接：它先安装更新的规则，再禁用首屏样式表。此前使用的 `css-only` 模式直接修改链接 href，冷模块加载期间的更新暴露了整块样式暂时失效的帧；不能据“没有水合错误”断言样式交接连续。字体声明独立于动态 StyleX 规则，不随该表更新。生产仍使用构建时注入的入口 CSS，不增加自制的补样式或更新机制。

名单的列宽交给 CSS 列模板与容器查询，移除服务端按字数估算、浏览器用 Canvas 测量的两套首帧宽度。模板通过页面局部 CSS 变量同时供表头与各行使用，不给通用 Table 增加 subgrid 模式；宽容器保留五种待办列，并限制姓名列占比、留出总分与行菜单的间距。分数到达不更换结构。人员权限页的卡片、简表和矩阵在服务端具有相同数据，由 CSS 从首帧选择可见形状；水合测量只淘汰隐藏树，不决定首次显示哪一种。开发验收逐帧检查冷页面的横向位置、宽度和父层动画；生产验收阻塞脚本，对照三种宽度的权限事实、图标和行的位置，并延迟总分检查原行是否保留。

开发慢模块导致的第二次骨架另有原因：已显示的服务端名单仍在等待客户端代码，祖先 Context 的同步更新会让 React 放弃该边界的选择性水合，重新挂载仍需等待模块的客户端树；它不会必然产生水合错误，也不是第二次文档导航。工作区能力发布按成员比较去重并以 transition 更新，根主题的浏览器偏好采用同样不打断待水合内容的更新优先级。启动脚本和产品 ThemeProvider 统一拥有根主题属性，Mantine 只消费 scheme、不回写根属性；减少动态效果的静态策略由 HTML 声明，避免其初始浅色覆盖启动脚本的深色。路由采用公开的 `routeDiscovery: { mode: 'initial' }`：授权 manifest 已包含完整路由目录，不再为链接发现产生额外的路由 Context 更新；未访问页面的实现仍由 RSC 选择和交付。

开发验收主动延迟名单客户端模块，并将服务端名册读取推入流式分支，要求可见名单出现后不能消失、不能重放整块入场动画；系统深色、与系统相反的显式浅色和显式深色都逐帧核对根主题。此前只按同一 DOM 节点检查位移，会漏掉节点被删除后重新创建的空窗，现已补上连续可见性约束。

紧凑枚举不依赖宿主的 `Intl.ListFormat` 语言数据：同一 `zh-CN` conjunction/narrow 调用在当前 Node 与开发用 Bun 分别生成顿号和“和”。`useList` 保持原有接口，使用编译消息声明的中文顿号、英文逗号分隔，空、单项、双项与多项在两端确定一致，不增加运行时识别分支或 Intl polyfill。

人员详情侧栏的参评批次和申报数量按已有 slot `prefetch` 接口准备，复用徽标的查询 key 和分页读取；首屏成功结果先进入文档的共享 Query 缓存。桌面与紧凑侧栏会渲染同一徽标的多份实例，不能让先水合的一份取回数量后，尚未水合的一份以新数量覆盖原本为空的 HTML。生产暖缓存组件栈已将这一失败定位到 `SectionBadge`；没有用隐藏首帧或忽略水合错误处理它。验收中的会话导航改用可见链接的真实点击，保留水合事件重放；仅观察到 router 全局对象就直接调用 `navigate`，不能证明 React 的恢复层已经挂载。流式轮廓验收读取到标题和行骨架两个标记后再断言，不假设两个标记一定在同一个网络 chunk。
