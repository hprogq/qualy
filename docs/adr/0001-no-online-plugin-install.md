# ADR 0001:插件拓扑对单个进程不可变

- 状态:**已接受**(2026-08-05)
- 相关:docs/assembly-design.md、[ADR 0002](0002-effect-as-the-backend-runtime.md)

## 背景

Cordis 提供的是动态插件运行时:service 出现或消失时,依赖它的 fiber 自动卸载与重启;插件缺少
依赖时保持 pending 等待;HMR 能在进程内换掉一个插件的代码。这是它最独特的能力,也是本项目
一直在用的能力。

同时,阶段 1 与 1.5 把装配推向了另一个方向:`qualy.yml` 是产品清单,`qualy.lock.json` 是被提交、
被 frozen 校验的解析结果,迁移有自己的 lineage,部署与启动分离。这是**不可变装配制品**的语义。

两套语义并存,而且互相矛盾:一边说装配在部署前就已经锁定,另一边说服务可以在进程内出现、消失
并触发插件重启。

## 决定

**一个 Qualy 进程启动后,插件拓扑不再变化。** 具体地:

- active plugin set、service 图、route 图、permission 目录、UI contribution 集合,启动后全部固定
- add / enable / disable / remove / purge / upgrade,以及任何需要重新初始化资源的配置变更,
  一律产生新的 assembly artifact,并要求滚动重启
- **启动全有或全无**:解析期发现依赖缺失就拒绝生成 lock;启动期发现某个能力构建失败,整个实例
  启动失败。不再有「插件 A 缺服务所以 pending,其余插件继续提供不完整服务」这种状态
- 需要在线调整的业务能力走 feature flag、租户设置、策略或 provider 启停,**不是**卸载代码模块。
  某个租户要停用本地登录,改的是认证策略,不是卸载 auth-local 插件
- 开发期不再追求插件级 HMR,后端改为进程重启(前端 Vite HMR 不受影响)

## 理由

一个 Qualy 业务插件同时携带 PostgreSQL schema、baseline SQL、迁移、provision、后端 service、
API contract 与 router、RBAC 权限目录、Web 页面与 UI contribution。「在线安装 org 插件」实际上
等于同时完成改库结构、载后端代码、更新权限目录、重建 router、部署前端资产、更新所有副本、
初始化租户数据、放开流量——这不是单进程热插拔问题,是一次完整发布。

多副本下更明显:实例 A 装了插件 X、实例 B 没装、数据库已经跑过 X 的迁移、CDN 还是旧 bundle,
这几件事没法长期共存。数据库、API contract、前端 bundle 和权限目录必须作为一个 artifact 协同发布。

企业系统不是不能接受重启,是不能接受不可控、不可观测、局部状态不一致的**进程内组件自重启**。
滚动发布/蓝绿/维护窗口重启都是标准操作,而且比进程内插件自行卸载重载更容易保证一致性。

## 后果

- Cordis 的动态激活、自动卸载、服务恢复重启与 HMR 不再是产品需求。它们目前主要被用来实现
  一种静态装配的便捷写法,而不是产品真的需要动态性
- 「插件可组合」不等于「插件可在线热插拔」;插件选装 = 构建/部署时选择装配;插件启停 = 生成新
  lock 并滚动发布;业务功能开关 = 运行时配置
- 这条决定独立于用什么运行时。即使继续用 Cordis,上述语义也应当成立;只是成立之后,Cordis
  的独特价值所剩不多,这是 ADR 0002 的前提
