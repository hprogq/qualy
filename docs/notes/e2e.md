# 端到端旅程与容量基线(2026-09-30)

## 旅程(`pnpm e2e`)

`tools/quality/e2e-stack.ts up` 在本机起一个完整部署:发布镜像(`pnpm release:build e2e`,Apple 芯片上加 `--platform linux/arm64`,
amd64 在转译下 vite 构建段错误)+ `deploy/compose.yaml` + 本地 TLS 边缘(Caddy `tls internal`,因为生产进程拒绝非 https 的公网地址)+
经 `deploy/demo/restore.sh` 导入的演示基线(与复原公开演示同一个脚本,五个账号用本实例固定的测试口令,口令不能含账号名,
密码策略会拒)。每次 `up` 都从基线重置,约 25 秒。旅程在 `tools/e2e/*.journey.ts`,`vitest.e2e.config.ts` 串行执行:

| 旅程          | 走过的路                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| review        | 辅导员按人员打开学生的竞赛申报 → 取回学生上传的证书(200、图片)→ 通过(等「1 秒后提交、可撤回」窗口过去后的真实请求)→ 学生重新登录看到「已通过」 |
| supplement    | 学生对「要求补充」作答:上传盖章页 PNG + 说明 → 辅导员在同一申报里看到说明与附件链接                                                            |
| session       | 登录后打开「我的成绩」→ 会话清掉 → 刷新被带到登录 → 重新登录回到原页                                                                           |
| phone         | WebKit iPhone 13:申报页目录树滚到底,最后一项在底部栏之上(今晚修的缺陷,修复前的镜像上这条失败)                                                  |
| accessibility | axe-core(WCAG 2.1 A/AA)扫登录、批次列表、我的申报、我的成绩、审核队列,不许 serious / critical;首轮只有审核队列分段标签对比度 4.47(已修)        |

失败的旅程在 `.qualy/e2e/artifacts/<旅程>/` 留下 `trace.zip`(`npx playwright show-trace`)、整页截图与控制台 / 网络日志。

**只在本机跑,还没进 CI**:演示基线不在仓库里(生成一次两小时)。进 CI 要先决定基线从哪来——例如作为构建产物发布、CI 下载——这是待定项。
基线的进行中批次处在「材料审核」:学生不能新建或提交申报,所以「填报 → 提交」的旅程要一份停在填报阶段的基线(`demo:seed --stage=entry`)。

## 容量基线(`node tools/benchmarks/capacity/run.ts`)

`record.ts` 用真实浏览器以学生和辅导员身份打开关键页面,记下每页发出的 API 请求与会话;`load.js`(k6,镜像按 digest 固定)在部署的内部网络里
直接打服务中的那一色:每个虚拟用户依次打开这些页面,一页的请求一起发(每主机 6 个,与浏览器相同),页间停 1–3 秒;`run.ts` 同时每两秒采样
server 容器的 CPU 与内存。**只打本机的一次性部署,从不打生产。** 只有读:基线在审核阶段。

2026-09-30 本机首轮(发布镜像 `8b60dd9f7`,Docker Desktop 12 核 / 8 GB,server 容器沿用 compose 的 768 MiB 上限;每档 20 s 爬坡 + 60 s 保持):

- **学生**:50 人同时时整页 p95 约 1.1 s;100 人时吞吐停在约 220 req/s(与 50 人时的 219 几乎相同),CPU 从 125% 升到 177% 而吞吐不涨,
  整页 p95 6 s——拐点在 50 到 100 人之间,瓶颈在 server 进程。学生的页面比审核员的重。空闲时逐个计时(各取三次中位):`me/entries?limit=200` 56 ms,是其余读的 2–4 倍(批次列表 31、`score-groups` 25、`standing` 19、`me/result` 15 ms),且「我的申报」与「我的成绩」都要它——它是下一步剖析的对象;先前猜的沙箱计分(`me/result`)并不重。
- **审核员**:100 人时 350 req/s、整页 p95 1.8 s。
- 全程零失败(无 4xx / 5xx / 断连),内存峰值 391 MiB,在 768 MiB 上限内。
- **这些数字不能直接当生产容量**:生产是 4 vCPU 至强 2.4 GHz,本机是 12 核;要么在同规格的一次性机器上重跑同一套脚本,要么只拿它比较版本前后。
  「截止前集中提交」与「登录」(Argon2)两个场景还没有:前者要填报阶段的基线,后者要避开登录限流与验证码,都需要先定怎么测。
