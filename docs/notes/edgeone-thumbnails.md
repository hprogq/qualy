## 实测方法与结果

通过正式函数的代码副本 `image-probe-07b8ac30` 和请求头 `EO-Function-Replica-Name` 隔离测试流量；副本继承现有环境变量。探针使用唯一对象
`attachments/8c32bab0-aad5-4d38-b9eb-09998ba7bb65/07b8ac30-023a-4f4d-986f-8776892b457d` 的四个版本，通过生产服务器发出请求。本机代理链路不作为 EO 联调依据。

先对两个 PNG 版本运行 28 个请求：原件、320 像素 PNG、320 像素 WebP、640 像素 PNG 交替请求三轮，再检查正式原件交付。真实尺寸和像素区分了不同版本，重复结果 SHA-256 稳定，后续请求命中缓存；两版原件在处理前后均与上传字节一致。随后加入 EXIF Orientation=6 的 JPEG、容易转码变大的 PNG，检查固定规格、回退与 HEAD。

最后使用仓库构建出的完整交付函数和真实 ES256 凭证，在副本执行 43 个请求：四版本各两轮 HEAD → 缩略图 GET → HEAD → 原件 GET，加七个拒绝请求、四个正式原件请求。结果如下：

| 合成样本      | 原件                             | 固定缩略图结果          | 结果大小 | 缓存     |
| ------------- | -------------------------------- | ----------------------- | -------- | -------- |
| 横向 PNG      | 1280×960，8863 B                 | WebP，640×480           | 6650 B   | 后续 HIT |
| 纵向 PNG      | 960×1280，9449 B                 | WebP，480×640           | 7140 B   | 后续 HIT |
| 方向标记 JPEG | 1200×800，17180 B，Orientation=6 | WebP，427×640，方向正确 | 898 B    | 后续 HIT |
| 密集棋盘 PNG  | 640×480，3941 B                  | 原 PNG，SHA-256 不变    | 3941 B   | 后续 HIT |

HEAD 均无正文，MIME 和 Content-Length 与对应 GET 一致；HEAD 之后 GET 的字节正确。七个拒绝结果：缩略图 Range 416，外加图片参数 400，过期/未知规格/缺失大小/签名篡改各 403，直接访问已缓存内部对象 403。四版正式下载前后均保持原件 SHA-256。

第一次完整签名矩阵因一次传输连接重置中断，保留记录后完整重跑通过；不将中断计为通过。合成文件、逐请求 JSON 与校验记录保存在本机 `/private/tmp/qualy-image-probe/`，属于临时证据，不作为长期发布物，也不包含签名私钥、内部密钥或完整 JWT URL。

## 原生体积回退的实际差异

[ImageProperties](https://cloud.tencent.com/document/product/1552/105342) 提供 `avoidSizeIncrease: true`。本次在该参数明确开启时，以 `width: 320, fit: contain, format: webp, quality: 88, stripExif: true` 处理 9449 B 的纵向 PNG，仍得到 21312 B 的 WebP；加入独立查询缓存标识后，MISS 与 HIT 都复现。这里只记录本次运行时和参数组合，不能推断该参数在所有环境都失效。

正式预设保留该选项，并补充可验证的保护：缩略图 JWT 携带附件记录中的真实原件大小；处理响应没有可信长度，或长度大于原件时，取消未消费的响应流，通过同一 EO 域名读取同一版本原件。最多增加一次读取，不缓冲整份文件，不返回 COS 直链。回退后使用实际图片类型与长度，不能把 PNG 标成 WebP。

此回退是体积优化，不是去 EXIF 的隐私承诺：返回原件时，其尺寸和元信息也随原件保留。固定缩略图是展示优化，不能承担证据原件、统一尺寸保证或敏感元信息清洗职责。

## 代码约定

- 首版只有 `thumbnail-v1`，由 `src/edgeone/thumbnail.ts` 固定为最大 640×640、保持比例、不裁剪、WebP、质量 82、去 EXIF、避免体积增大。PNG/JPEG/WebP 可以签发；GIF、AVIF、PDF 等继续使用原件。修改规格行为必须使用新名称。
- 原件 JWT 字段及 `/v1/<JWT>` 地址保持不变。缩略图额外且必须带 `p: thumbnail-v1` 和 `b: 原件字节数`；二者与对象 key、版本、文件名、源 MIME、issuer、audience、iat、exp 一起签名。仍为 ES256，正常/最大寿命 60 秒，偏差 3 秒。未知规格、额外字段、任意查询参数被拒绝。
- 外部参数不进入 `eo.image`。验签后才读取 `/attachments/...?...versionId...&qualy-preview=thumbnail-v1`；规格与版本在当前保留查询参数的缓存键下隔离。原件读取不带处理参数或规格标识。
- 缩略图不支持 Range，不转发原件条件头，不复制原件 ETag 或 Last-Modified。响应 MIME 使用实际安全光栅类型，长度来自实际表示，`inline` + `nosniff` + `private, no-store`；原件的 attachment 文件名、Range 与条件读取保持原行为。
- storage 授权后将数据库记录的大小传给 provider。EO provider 可在原件目标旁附带缩略图目标，业务描述只投影该结果，不认识 EO 参数。浏览器卡片使用缩略图，大图与下载仍从内容端点重新授权读取原件。缩略图与灯箱的失败预算分别限制为一次，复用同一描述查询进行并发合并。
- 本地和直连 COS 不提供该派生目标，卡片继续原有图片路径；EO 模式的所有目标仍属于 files 域名，任何失败都不切换到直连模式。

## Passthrough 与地址形状

在内置浏览器核对了 [Fetch/Passthrough 教程](https://cloud.tencent.com/document/product/1552/120717)、[Request](https://cloud.tencent.com/document/product/1552/81902)、[FetchEvent](https://cloud.tencent.com/document/product/1552/81899)、[复杂回源 URL 重写](https://cloud.tencent.com/document/product/1552/118931) 和图片处理示例。

`/v1/<JWT>` 不是 COS 强制要求。直接对象路径加签名查询参数同样可以设计安全协议，前提是签名覆盖路径、真实 `versionId`、时效及全部读取指令。当前保留交付地址与内部缓存地址分离，是为了稳定缓存键、控制响应、以及保留已实测的函数停用拒绝边界。此前联调时免费套餐未能应用自定义 Cache Key；本轮沿用保留查询参数的配置，直接透传每次变化的签名查询可能碎片化缓存。若后续控制台允许应用并实测验证新的缓存策略，应重新评估此限制。实际存在的对象地址若唯一依赖函数授权，也不能沿用“函数停用后 `/v1` 在 COS 不存在”的旧验收结论。

官方 Passthrough 示例通过不调用 `respondWith` 透传当前请求；`Request.url` 只读，复杂重写示例仍然新建请求并 Fetch。本次未发现能让它替代 JWT 对象映射、响应投影和独立内部授权的接口。整个 Host 触发函数是另一项路由调整，不能仅凭调整触发范围删除 `QUALY_EDGE_KEY`。图片示例中的 `passThroughOnException()` 不适用于本服务，继续受控拒绝异常。

`QUALY_STORAGE_COS_EDGEONE_THUMBNAILS` / manifest `edgeOne.thumbnails` 默认 false，环境覆盖清单。先部署支持该签名预设的边缘函数，确认原件仍正常，再在包含本轮代码的应用 release 中开启；无需改 DNS、开启五个全局图片开关或放开外部图片参数。生产部署仍需用户确认。

## 真实材料验收（2026-10-28）

用户指定的测试审核记录共 8 份附件：COS 上 4 张 JPEG、1 张 PNG 进入缩略图规格；1 张 local 后端 JPEG 不经 EO；PDF 与 DOCX 不生成缩略图。验收只读，不修改材料。

方法与上文一致：正式函数的代码副本 `thumb-accept-1028` 部署仓库当前构建的交付函数（含 `thumbnail-v1`），凭证在生产容器内用服务端自己的签名密钥签发，经 `EO-Function-Replica-Name` 只把测试流量送到副本。每份图片依次请求：正式函数原件、两次缩略图（第二次换新凭证）、副本原件、正式函数原件。

| 样本          | 原件 → 缩略图                                | 文字与印章                                                         | 码                                   |
| ------------- | -------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------ |
| 盖章名单照片  | 1080×1824 JPEG 103 KB → 379×640 WebP 12.5 KB | 标题、25 组学号姓名、日期可读；印章形状清楚，环形文字不可读        | 无                                   |
| 73 行名单照片 | 1280×1707 JPEG 163 KB → 480×640 WebP 18.7 KB | 标题、表格结构、手写批注、印章可辨认；**表内学号姓名不能可靠辨认** | 无                                   |
| 低清证明      | 546×766 JPEG 55 KB → 456×640 WebP 11.5 KB    | 与原件基本一致                                                     | 无                                   |
| 软著证书      | 944×1256 PNG 2.3 MB → 481×640 WebP 59.8 KB   | 全部文字清楚，印章环形文字部分可读                                 | **原件二维码可解码，缩略图不可解码** |
| 荣誉证书      | 830×594 JPEG 238 KB → 640×458 WebP 91 KB     | 全部文字可读                                                       | 无                                   |

结论：

- 五份缩略图均为 WebP、保持比例、长边 640，没有放大较小原件（低清证明长边 766 缩到 640）；同规格重复请求命中缓存且字节相同。
- 三条读取路径上的原件字节数等于记录大小，SHA-256 一致；验收前后正式函数交付的原件不变。
- 缩略图只用于在卡片里认出是哪份材料。二维码在软著证书原件中约 85 像素宽，缩略图中约 43 像素；226 字符的二维码此时每个模块不足 1 像素，物理上无法解码。密集表格、印章环形文字和二维码必须打开原件核对，这与“大图和下载始终使用原件”的设计一致。原件中的另一枚二维条码（PDF417）在原件中也无法解码，与缩略图无关。
- 解码使用 Chrome `BarcodeDetector`（macOS Vision），只比对格式、长度和内容摘要，不记录内容。
- 第一次运行时首份样本的缩略图返回 `403 invalid`：副本刚创建，请求落到不认识 `p` 字段的正式函数；第二次运行全部通过。不将第一次计为通过。

验收用的材料副本已从生产容器、服务器和本机删除，只保留大小与摘要记录。卡片中的实际显示效果在应用开启缩略图后另行检查。
