# 首屏性能与 Lighthouse

## 怎么量

`pnpm lighthouse [页面…] [--runs 3] [--form mobile|desktop|both]`(`tools/quality/lighthouse.ts`)对
`node tools/quality/e2e-stack.ts up` 起的本机部署跑分:一个 Chrome,按 E2E 旅程的方式在登录页登录,Lighthouse
经调试端口在同一个浏览器里开自己的标签页,所以每次都带着真人会有的会话(Lighthouse 两次运行之间清缓存与 service
worker,不清 cookie)。默认四个页面:`login`(访客)、`batches`、`my-entries`(学生)、`org-tree`(管理员),
手机与桌面各跑三次取每项指标的中位数;报告与 `summary.json` 在 `.qualy/lighthouse/<时间>/`(gitignored),
表格里打印的是中位数,`summary.json` 另记每一次。

两个没选的做法:

- **不装成依赖**:把 lighthouse 13 加进 devDependencies 会经 @sentry/node 带进 @opentelemetry/api,pnpm
  随之改写 `packages/plugins/infra/sandbox` 的 `@effect/platform-node` 的 peer 解析——一个量东西的工具改动了
  镜像要装的生产依赖图。所以经 `pnpm dlx lighthouse@13.5.0`,版本钉在脚本里。
- **不用 Lighthouse CI**:@lhci/cli 0.15.1 固定 lighthouse 12.6.1,与 DevTools 里的 13.x 报告不可比;它的登录脚本
  钩子要 puppeteer。这里要的只是「同一个部署、同样的登录、同样的次数、取中位数」,几十行就够。

交互式诊断用 Chrome DevTools 的 Performance 面板或 Chrome DevTools MCP(`.mcp.json` 是每台机器自己的,
仓库不带)。

## 读懂手机端的分数(lantern 模拟)

手机档是模拟节流:150 ms RTT、1.6 Mbps、CPU ×4。实测时页面在本机几十毫秒就加载完,分数来自把实测的请求与主线程任务
放进依赖图后按节流重算。读 `@paulirish/trace_engine` 的 `lantern/metrics` 实查到三件事:

- **FCP 只算首帧前结束的「阻塞渲染」请求,而首帧前执行过的脚本都算阻塞渲染。**原先 `<head>` 里的样式表挡住首帧,
  等它到时入口的整个模块图也已下完并执行,于是首帧前执行过的全部 modulepreload(约 400 KB)都进了 FCP——所以四个页面的
  手机 FCP 都是 2.87 s,与页面无关。启动画面本来是内联样式、不需要那张表。
- **LCP 两张图都包含 LCP 之前结束的所有请求**(低优先级图片除外)。LCP 本身是 TTFB、关键请求被发现的延迟、下载、
  JS 解析与执行、React 渲染、主线程阻塞、LCP 元素的渲染延迟这几段相加;在这个应用上,首屏要下的字节(约 676 KB)与请求
  串行的层数占了大头,但下一轮应先看 Lighthouse 的 LCP 分段与 Performance trace,而不是只盯总字节。
- **定时器等待在模拟里会被压缩**:依赖图只有网络与 CPU 节点。React 的 300 ms Suspense 节流、落地动画这类等待对真人
  存在,对跑分几乎不可见——改它们要按真人的收益来判断,不要按分数。

本机多次运行之间方差很大(同一构建的手机 FCP 在 0.8–2.0 s 之间):本机下载模块只要几十毫秒,与首帧的先后并不固定。
所以一律取多次中位数,并且**分数不等于真人体验**——下面用应用节流(Slow 4G + CPU ×4,真实时间轴)另做 A/B。生产环境另测。

## 真人时间轴:节流 A/B(2026-09-30)

`.qualy/lighthouse/filmstrip.ts` 式的做法(本地脚本,不进仓库):Playwright 开真 Chrome,`Network.emulateNetworkConditions`
(RTT 562.5 ms、下行 1474.56 kbps,即 Lighthouse 手机档换算成应用节流)+ `Emulation.setCPUThrottlingRate(4)`,禁缓存,
学生登录后打开批次列表;注入脚本记首帧、React 第一次往 `#root` 里画东西的时刻(并检查那一刻壳样式表是否已生效)、
进行中批次卡片标题出现的时刻、LCP 与 CLS,同时录 trace 截图。同一构建上的变体靠改写返回的 HTML 得到(两种都经同一个
路由,只有字节不同);「改动前」是用改动前的提交单独构建的镜像。每组 5 轮取中位数:

|                                | 首帧 | React 首次提交 | 提交时样式已生效 | 页面内容出现 | LCP  | CLS       |
| ------------------------------ | ---- | -------------- | ---------------- | ------------ | ---- | --------- |
| 改动前的构建                   | 2548 | 3044           | 5/5              | 8265         | 8296 | **0.347** |
| 现构建,改回阻塞样式表          | 2752 | 3042           | 5/5              | 7582         | 7608 | 0.008     |
| 现构建,样式表延后              | 92   | 3052           | 5/5              | 7593         | 7612 | 0.008     |
| 现构建,样式表延后 + 语言包预取 | 96   | 3346           | 5/5              | 7585         | 7612 | 0.008     |

读法:

- **样式表延后只提前了首帧**(启动画面从约 2.6–2.8 s 的白屏变成约 0.1 s 出现),React 提交与页面内容一点没提前;
  没有未样式化的帧(React 提交时样式表 5/5 已生效——入口等的是 `load` 事件,不是挂上就渲染),CLS 不变。这是真实的
  体验改善(慢网下不再白屏近 3 秒),但远没有 FCP 分数的变化那么大。
- **语言包预取没有收益**:内容出现时间不变,React 提交反而晚约 300 ms(带宽受限时它与首批脚本抢带宽)。已在提交前撤回,
  内联启动脚本与 CSP 哈希恢复原样。
- **内容提前约 670 ms、CLS 0.35 → 0.008 来自其余改动**:冷启动时页面代码与布局一起预取(少一轮串行加载与一次 300 ms
  节流)、批次列表的卡片与占位。这个 CLS 与最初生产报告里的 0.35–0.42 一致。

## 这一轮改了什么(2026-09-30)

- **样式表不再挡首帧**:构建把壳唯一的 `<link rel="stylesheet">` 改成 `preload`(`qualyShellStyle`,
  @qualy/web-build),入口在 React 渲染前把它插回原位置并等它的 `load`(`apps/web/src/shell-style.ts`)。开发态没有这条 link,
  什么也不等。失败时照旧无样式地画出来,内联看门狗照旧听到样式表的 error。
- **冷启动时当前页面的代码与布局一起预取**(`RuntimeLoader`):原先布局到了才渲染路由,页面组件再 lazy 一次,
  隔着 React 的 300 ms 揭示节流;页面自己的数据请求要等页面画出来才发。
- **@mantine/dates 从组件库 chunk 拆出**(`dates` 组,`includeDependenciesRecursively: false`):首屏组件库
  chunk 105.8 → 88.8 KB(gzip),没有首屏用日期选择器;递归收依赖会把 @mantine/core 的一部分一起拉走,
  两块都进首屏,所以关掉。chunk 图门禁照常通过,无环。
- **批次列表的布局偏移**:进行中批次的卡片不再放在列表的加载区里——原先「进行中」的查询先答,卡片占位随之撤掉,
  列表上移,列表答复后卡片再出现,列表又下移。卡片等「进行中的批次」和「我在其中的待办」都到了才画(待办行晚到会撑高卡片),
  占位按手机与桌面各自的形状画;列表占位补上「全部批次」这一行,手机上按卡片行而不是五列表格画。刷新时的小转圈从分段
  控件左侧挪到右侧,且不论是否显示都留着位置,筛选时分段控件与搜索框不再左右跳。
- **无障碍**:组织树展开按钮 22 → 24 px(缩进同步 22 → 24);批次切换按钮与登录页语言按钮的可访问名称由按钮上可见的
  文字组成(WCAG 2.5.3);40 处以次要灰 85% 画的小字改回次要灰本身(浅色背景上 3.65–3.99:1 → 4.90–5.51:1,深色
  3.97–4.57:1 → 4.95–5.91:1)——tokens.css 本就写着「文字只用三种灰」,85% 是绕开这条规则的第四种灰;由它再混出的背景
  与分隔符保持原值。另有 15 处以次要灰 50–80% 画的小字(已结束阶段的标题、日期与徽标、尚未计入的分数、类型名、斜体的
  「无」、代码行号等)同样改回次要灰:浅色都不是唯一区分,另有徽标文字、字重、斜体或底色;图标、分隔符、拖动把手与禁用态
  不在 4.5:1 要求内,不动。E2E 的 axe 旅程加上组织树(管理员)与批次概览(辅导员)——后者正是查出已结束阶段那几处的页面。

## i18n:英文默认文案与中文语言包

口径(当前构建;服务端发 brotli,Lighthouse 记录的 transferSize ≈ brotli 大小加响应头):

|                                              | 原始   | gzip    | brotli |
| -------------------------------------------- | ------ | ------- | ------ |
| 中文语言包(1 个 chunk,所有插件的 zh-CN 译文) | 270 KB | 67 KB   | 53 KB  |
| 各插件 `client/i18n.ts` 所在的 11 个 chunk   | 443 KB | 98.5 KB | 83 KB  |

后者进首屏,是因为聚合模块从每个插件的 `client/i18n.ts` 取 `catalogs` 与 `errorMessages`,而那个模块同时定义了该插件
全部消息描述符(`{ id, defaultMessage }`,英文默认文案就在里面),模块不能按导出拆开;登录页也要下载全部插件的。中文
读者因此同时付英文默认文案与中文译文两份。

PoC(不进仓库):构建期插件把浏览器代码里静态描述符的 `defaultMessage` 换成空串(4193 条),只留 id,其余不变。
结果:

- 那 11 个 chunk:原始 443 → 313 KB,gzip 98.5 → 51.6 KB,brotli 82.8 → 43.7 KB;剩下的是 id、结构与错误翻译函数。
- Lighthouse 记录的 LCP 之前传输量,四个页面各少约 40 KB:login 558 → 518、batches 660 → 620、my-entries 791 → 751、
  org-tree 645 → 606(KB,三次中位数)。
- 手机 LCP(Lighthouse,三次中位数,同一时段先后跑):login 3665 → 3663、batches 4227 → 4078、my-entries
  5127 → 4750、org-tree 4070 → 3920(ms)。节流时间轴(批次页,5 轮):React 提交 3045 → 2853、内容出现 7600 → 7384(ms)。
- 英文读者改为下载 en-US 语言包:4193 条默认文案作 JSON 约 165 KB 原始、42 KB gzip,与现在内联的量相当,不增不减。

正式做要解决的不只是抽取:I18nProvider 在语言包加载失败时靠 `defaultMessage` 显示英文,抽掉后要改为回退到 en-US 语言包;
catalogs 门禁要把 en-US 当作与 zh-CN 同等的语言包校验;服务端传来的 `UiText` 自带 `defaultMessage`,是另一种表示,不受影响。

## 没做、需要决定的

- **RUM 厂商 SDK**:先不动。没有生产 trace 证明它在 LCP 关键路径上;真要推迟,得先确认早期错误、首次交互、导航与
  LCP/CLS 都能经 buffered PerformanceObserver 补回,否则就是为跑分牺牲监控。
- **详情页的 `sync` 重读**:批次的事件流连上先发 `sync`,页面把连接建立之前可能漏掉的变更重读一遍——首屏每个查询
  都会在约 300 ms 后再请求一次。这是有意的正确性选择,发生在 LCP 之后,不影响分数,只多一倍首屏读。
- **组织树桌面端 CLS 0.096**:加载占位是通用的 `EditorSkeleton`,比树短,页脚先停在视口底部再被树推下去。按树高画占位
  对小树会反向跳;让页脚总在折叠线以下则改变「短页面页脚贴底」的设计。
